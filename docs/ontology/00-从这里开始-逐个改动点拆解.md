# 00 · 从这里开始：逐个改动点拆解（最接地气版）

> 如果 01/02 觉得太"理论先行"，**从这篇看**。这里不讲大词，只做一件事：
> 把"系统要改哪几处"拆成一个个**原子改动点**，每个点都按同一套六面拆开，全程用真实代码/数据 + 一个具体场景，让你有体感。
>
> 每个原子的六面：
> 1. **🎬 场景**：用户做了件什么事
> 2. **📷 现在怎么做的**（看真实字段/代码）
> 3. **❌ 问题在哪 / 为什么要改**（对应一个真实 bug）
> 4. **✅ 改成什么样**（BEFORE → AFTER 数据对比）
> 5. **🏭 业界别的做法 + 优劣**
> 6. **📚 这在本体论里是什么原理**（一句话）

先给全景，再逐个拆。

---

## 全景：要改的就这 6 个原子

专访 1.0 现在是"一堆数组 + 关系藏在字段里"。要做的事一句话：**把"关系"和"规矩"从藏着，变成明面上的一等公民。** 拆成 6 个原子：

| # | 原子改动点 | 一句话 |
|---|---|---|
| A | 关系不再藏在字段里 | `relatedThemeIds` 这种"藏在资产里的 id" → 独立的「边」 |
| B | 证据来源统一成"溯源边" | 散落的 `EvidenceAnchor` → 统一的 `derived_from` + 来源标签 |
| C | 两套连线合并成一套 | `MemoryEdge`(独立) 和 `relatedThemeIds`(内嵌) 做同一件事 → 合一 |
| D | 给认知资产一个"家族树" | 观点/决策/笔记…其实是兄弟，但系统不知道 → 显式父类 |
| E | 把"规矩"写成系统能自动查的条款 | `clampMaturityByAppearances` 等散落规则 → 显式公理 |
| F | 删东西连带删干净 | 删会话留下一堆孤儿 → 级联删除 |

下面一个个拆。

## 原子 A：关系不再藏在字段里

### 🎬 场景
你在一次专访里聊"放权"，系统抽出一条观点 P1「担心失控」，并判断它属于「放权」这条主题线。

### 📷 现在怎么做的
P1 这个观点对象里，塞了一个字段 `relatedThemeIds`：

```jsonc
// state.points 数组里的一项
{ "id": "P1", "title": "担心失控", "relatedThemeIds": ["theme-放权"] }
```

"P1 属于放权主题"这件事，**藏在 P1 自己身上的一个 id 数组里**。

### ❌ 问题在哪
这跟 01 里"狗表里的 `主人id` 列"是一模一样的毛病：**关系藏在一方身上，系统并不把"属于"当个东西**。具体痛在：

- **反查难**：想问"放权主题下都有哪些资产？"——你没法直接问主题，只能**把 points/questions/decisions/notes 每个数组翻一遍**，看谁的 `relatedThemeIds` 里有放权。漏翻一个数组就漏召回（审查里"召回漏 decisions"就是这么来的）。
- **加资产类型就得改 N 处**：以后多一种认知资产，所有"按主题聚合"的地方都得记得加上它。

### ✅ 改成什么样
把"属于"抽出来，变成一条**独立的边**（一条三元组：P1 —属于→ 放权）：

```jsonc
// BEFORE：藏在 P1 里
{ "id": "P1", "relatedThemeIds": ["theme-放权"] }

// AFTER：独立的一条边，谁都能查
{ "from": "P1", "type": "belongs_to_theme", "to": "theme-放权" }
```

### 🏭 业界别的做法 + 优劣
| 做法 | 谁在用 | 优 | 劣 |
|---|---|---|---|
| 内嵌 id 数组（现状） | MongoDB 等文档库 | 读单个资产快 | 反查难、关系无属性、易不一致 |
| 关系型外键 + join 表 | MySQL/Postgres | 成熟、约束强 | 多对多要建中间表，关系仍"无名" |
| **独立的边对象**（本方案） | 图思维/轻量 | 双向可查、关系一等、能挂属性 | 要维护一张边集合 |
| 图数据库原生边 | Neo4j | 边是头等公民、查询强 | 引入重数据库（本场景过重，见 SurrealDB 评估） |

我们取"独立的边对象"这一档：**拿到图的好处，不背数据库的重量。**

### 📚 本体论原理（一句话）
**关系要做"一等公民"**——01 §1 那句"关系是一等的、带语义、可推理"，落到代码就是这一步。

## 原子 B：证据来源统一成"溯源边"

### 🎬 场景
观点 P1「担心失控」是从你第 7 轮发言里抽出来的。点开 P1，你想看"这是我哪句话说的？"——这就是证据链。

### 📷 现在怎么做的
P1 上内嵌一个"锚点"结构，指回那一轮：

```jsonc
{ "id": "P1", "evidenceAnchors": [{ "sessionId": "S3", "turnId": "T7" }] }
```

但同样语义的"来源"，在不同地方**长得不一样**：笔记用 `keyQuoteAnchor`，主题用 `representativeQuoteAnchor`，记忆又有自己的 `sourceType`……**同一件事（这东西从哪来）有好几种写法。**

### ❌ 问题在哪
- **七零八落**：要做"敏感来源不进对话召回""LLM 抽的别当成事实"这类治理，得在每种写法上各写一遍过滤（审查里这些规则确实是各处手写、容易漏）。
- **没有"谁负责"**：现在只记了"从哪轮来"，但没结构化记"**这是 LLM 抽的还是你确认的**"——而这恰恰是判断"能不能当事实用"的关键。

### ✅ 改成什么样
统一成一种**溯源边** + 一个**来源标签**：

```jsonc
// AFTER：一条 derived_from 边，边上挂"溯源信息"
{
  "from": "P1", "type": "derived_from", "to": "S3#T7",
  "provenance": { "origin": "llm_extracted", "turnId": "T7", "confidence": 0.8 }
}
```

`origin` 取值就几种：`llm_extracted`（AI 抽的）/ `user_confirmed`（你确认的）/ `imported`（外部导入）…… 治理时只看这一个字段。

### 🏭 业界别的做法 + 优劣
| 做法 | 优 | 劣 |
|---|---|---|
| 不记来源，直接信 | 简单 | AI 幻觉混进事实，无法追责 |
| 各处一个临时 `source` 字段（接近现状） | 灵活 | 口径不一、治理要重复写 |
| **PROV-O 标准溯源**（本方案的轻量化） | 统一、可治理、回答"从哪来/谁负责" | 要先约定标准 |
| 内容寻址 / 区块链存证 | 防篡改强 | 对个人工具过度 |

### 📚 本体论原理（一句话）
这就是 **PROV-O 溯源本体**（01 §4.8）：任何信息都该能回答"从哪来、谁负责、怎么生成"——像鸡蛋上的溯源码。

## 原子 C：两套连线合并成一套

### 🎬 场景
一条长期记忆「倾向亲自把关」也跟「放权」主题相关。

### 📷 现在怎么做的
**观点连主题**用内嵌的 `relatedThemeIds`（原子 A）；**记忆连主题**却用一张**独立的表** `MemoryEdge`：

```jsonc
// 记忆↔主题，单独一个数组 state.memoryEdges
{ "fromMemoryRecordId": "M9", "themeId": "theme-放权" }
```

同样是"X 挂在主题上"，**观点走一套、记忆走另一套**。

### ❌ 问题在哪
- **主题聚合要写两遍**：想列出"放权主题下的所有东西"，得既翻各资产的 `relatedThemeIds`，又翻 `memoryEdges` 表，两套逻辑拼起来。
- **多一套就多一处会漏**：审查里"`MemoryEdge` 与 `relatedThemeIds` 双轨"正是这个。

### ✅ 改成什么样
两套都变成**同一种边**，只是类型名不同：

```jsonc
{ "from": "P1", "type": "belongs_to_theme", "to": "theme-放权" }  // 观点
{ "from": "M9", "type": "about_theme",      "to": "theme-放权" }  // 记忆
```

聚合时一句"指向放权主题的所有入边"全拿到，不再分两套。

### 🏭 业界别的做法 + 优劣
- **现状（异构两套）**：历史演化的产物，灵活但碎。
- **统一边模型（本方案）**：一套机制、一处维护；代价是要做一次合并迁移。
- **完全独立的关系表 per 类型**（传统关系库风格）：约束清晰，但"看全貌"要 join 一堆表。

### 📚 本体论原理（一句话）
**同一种语义就该用同一种关系表示**——这是"概念化要一致"（01 §1 conceptualization）的直接要求；不一致就是"本体债"。

## 原子 D：给认知资产一个"家族树"

### 🎬 场景
观点、决策、知识债、笔记——你心里清楚"它们都是我沉淀下来的认知资产"。但系统里它们只是 4 个**互不相干**的数组。

### 📷 现在怎么做的
`state.points`、`state.decisions`、`state.debts`、`state.notes` ——平行的四个数组，**没有任何地方写着"它们是同一类东西"**。

### ❌ 问题在哪
- **共性逻辑反复抄**：导出、清空、敏感过滤、"都能溯源到某轮"——这些对四类资产都成立的事，现在每类各写一遍。
- **想统一处理就得手工列举**（又回到"召回漏一类"的根子）。

### ✅ 改成什么样
显式写出**家族树**（父类）：

```
认知实体 CognitiveEntity（可溯源、可归类、可治理）
├── 蒸馏类 Distillation → Note / Point / Decision / Debt   ← 这四个是兄弟
├── 追问类 Inquiry      → Question
├── 主轴类 Axis         → Theme
└── 记忆类 Memory       → MemoryRecord
```

有了"蒸馏类"这个父，凡是对蒸馏类成立的治理/召回/证据逻辑，写一次即可。

> ⚠️ 注意一个坑：能不能说"主题 Theme 是观点的一种"？**不能**。一条观点永远是观点（不变）；主题是很多资产**汇聚涌现**出来的轴，成员会增减、会成熟（会变）。"会变的"不能当"不变的"的父类——所以 Theme 单列成 Axis，不塞进资产层级。

### 🏭 业界别的做法 + 优劣
| 做法 | 优 | 劣 |
|---|---|---|
| 平行数组（现状） | 简单直白 | 共性逻辑重复、易漏 |
| OOP 类继承 | 语言原生、编译期检查 | 跨"数据"层不好序列化/演化 |
| **显式 taxonomy（本方案）** | 数据层就带分类、统一处理 | 要设计并维护层级 |
| 纯标签 tags | 灵活 | 无层级、无约束、易混乱 |

### 📚 本体论原理（一句话）
这是 **类层级 / subClassOf**（01 §4.2），而"主题为什么不能当资产父类"用的是 **OntoClean 刚性检验**（01 §4.6，"学生会毕业"那条）。

## 原子 E：把"规矩"写成系统能自动查的条款

### 🎬 场景
你的某条主题只在一次专访里出现过一次，系统却把它标成"已成型"——明显不对，成熟度该跟出现次数挂钩。

### 📷 现在怎么做的
这条规矩现在**写死在一个函数里**（`clampMaturityByAppearances`），藏在 finalize 流程深处。类似的规矩还有好几条，各自散落：敏感记忆别进召回、AI 抽的别当事实……**每条都埋在某个具体流程里，没有统一的"规矩清单"。**

### ❌ 问题在哪
- **看不见、容易漏**：新写一条链路时，很容易忘了某条规矩（审查里大半 bug 是"某条路径漏了某条规矩"）。
- **没法统一体检**：想问"当前数据有没有违反任何规矩？"——做不到，因为规矩没集中。

### ✅ 改成什么样
把规矩提成一份**显式公理清单**，由一个校验器统一跑：

```
A1 每条蒸馏必须有来源（没有=可能是幻觉，拦下）
A2 主题成熟度 ≤ 跟它相关的资产数量决定的上限    ← 现在那条规矩
A3 AI 抽的内容，未经你确认，不得当"事实"展示
A4 标了敏感的记忆，不进对话召回（除非你开开关）
A5 删一个东西，连它的所有关系一起删（见原子 F）
```

```ts
axioms.check(state) // → 返回所有违例，统一记审计/拦截
```

### 🏭 业界别的做法 + 优劣
| 做法 | 优 | 劣 |
|---|---|---|
| 散落 if 检查（现状） | 就近、直接 | 看不见全貌、易漏、难测 |
| 校验库（如 Zod/JSON Schema） | 成熟、声明式 | 主要校"单条数据格式"，跨实体规则弱 |
| **公理清单 + 校验器**（本方案，≈ SHACL 思路） | 规矩集中、可统一体检 | 要把散落规矩搬到一处 |
| OWL 推理机 | 表达力最强、能自动推 | 太重、开放世界假设不适合本场景（01 §4.4） |

### 📚 本体论原理（一句话）
这是 **公理 / 约束校验**（01 §4.9 SHACL）：像填表单时"手机号必须 11 位"那种**红框报错**——检查合不合规，而不是去推新结论。

## 原子 F：删东西连带删干净

### 🎬 场景
你删掉一次不想要的专访。

### 📷 现在怎么做的
删了会话本身，但它牵连的东西**靠各处手工记得去清**：那次专访的逐字稿向量块、指向它的证据锚点、相关索引……谁清谁不清，全靠开发记性。

### ❌ 问题在哪
**留孤儿**：审查里明确的跨库一致性问题——删了会话，它的 transcript 块还在向量库里，对话还会引用一个"已经不存在的会话"。

### ✅ 改成什么样
关系一旦都变成统一的边（原子 A/B/C），删一个节点就能**一把抓到它所有出入边**，连带删干净（这就是公理 A5）：

```ts
removeNode(state, "S3")
// → 删 S3，同时删：所有 from=S3 或 to=S3 的边、它的 turns、指向它的 derived_from…… 无孤儿
```

### 🏭 业界别的做法 + 优劣
| 做法 | 优 | 劣 |
|---|---|---|
| 手工各处清（现状） | 无需机制 | 极易漏 = 孤儿 + 数据泄漏 |
| 数据库外键 `ON DELETE CASCADE` | DB 自动级联、可靠 | 得用关系库 + 建好外键 |
| **统一边 + 级联函数**（本方案） | 在现有栈内做到自动级联 | 要先完成 A/B/C 的边统一 |
| 引用计数 / GC | 自动回收 | 实现复杂，对本场景过度 |

### 📚 本体论原理（一句话）
这是**引用完整性 / 级联**——关系成了一等公民后自然就能做到"删点连边"，是原子 A 的红利。

## 把 6 个原子串起来看

注意它们是**有依赖顺序**的，不是并列：

```
A 关系变成边 ─┐
B 来源变成溯源边 ─┼─→ 有了"统一的边" ─→ C 两套合一  ─→ F 删点连边(级联)
              │
D 家族树 ────┘                              E 规矩变公理(其中 A5 就是 F)
```

- **A 是地基**：关系先变成一等的边，B/C/F 才有可能。
- **D 正交**：家族树是给实体分类，独立推进。
- **E 收口**：把所有规矩（含 A5 级联）集中成公理清单，统一体检。

**一句话总结整篇**：现在系统把"关系"和"规矩"都**藏起来了**（藏在字段里、藏在函数里）；本体论重构就是把它们**翻到明面上、做成一等公民**——于是反查变易、共性只写一遍、规矩能自动体检、删东西不留孤儿。这，就是"用本体论重构"对这个系统的全部体感。
