## 1. 本体论是什么

### 理论

**哲学起源**。本体论（Ontology，源自希腊语 *ón* "存在" + *lógos* "学说"）是形而上学的一支，研究"**存在什么、它们如何分类、彼此如何关联**"。亚里士多德的《范畴篇》把存在划为十大范畴（实体、数量、性质、关系……）——这是人类第一次系统地问"世界由哪些**种类**的东西构成"。两个贯穿始终的哲学区分，后面会反复用到：

- **殊相 vs 共相**（particular vs universal）：这一杯具体的水 vs "水"这个类。
- **持续体 vs 发生体**（continuant vs occurrent）：在时间中保持同一性的"对象"（一个人）vs 在时间中展开的"事件/过程"（一次谈话）。

**计算机科学的转义**。1990 年代知识工程把这个词借走，赋予工程定义。最经典的是 Gruber（1993）：

> "An ontology is an explicit specification of a conceptualization."
> （本体是对一个**概念化**的**显式规范**。）

Studer 等（1998）补全为：**"形式的、显式的、共享的概念化规范"**（formal, explicit, specification of a shared conceptualization）。这句话堆了五个抽象词，**用"盖房子"翻译一遍就懂了**——它说的是"怎么把脑子里的想法，变成一张人和机器都认的图纸"：

| 原词 | 盖房子类比 | 大白话 |
|---|---|---|
| **conceptualization** 概念化 | 你脑子里想的房子长什么样、几个房间怎么连 | 你对某领域"有哪些东西、怎么关联"的**想法** |
| **specification** 规范 | 把想法画成**图纸** | 把想法**写下来**（别停在脑子里） |
| **explicit** 显式 | 图纸标清尺寸、材料、承重 | 写**明白**，不靠"老师傅都懂"的默契 |
| **formal** 形式 | 用标准制图法，施工队和造价软件都能读 | **机器能读能查**，不是一段散文 |
| **shared** 共享 | 全队按同一张图施工 | 大家**认同、能复用**，不是你一个人的草稿 |

所以一句话：**本体 = 一张把"领域里有什么、怎么连"画清楚、机器能读、大家公认的图纸。**

#### 和邻近概念的精确区别：用"狗和主人"爬一遍

这几个词（词表/分类法/Schema/本体/知识图谱）极易混。别背定义——拿**同一件事「狗、主人、养」**在每个层级里走一遍，差异立刻可感：

**① 词表**：只是查词，词之间没有连线。
> 狗：一种家养犬科动物。 主人：饲养宠物的人。

**② 分类法 Taxonomy**：一棵树，**只有"是一种"(is-a)这一种关系**。
> 动物 → 哺乳动物 → 犬科 → 狗。（像生物分类、电商类目）

**③ 叙词表 Thesaurus**：词表 + **几种弱关系**（同义/广狭/相关），但关系少、不严格。
> 狗 ≈ 犬（同义）；狗 ⊂ 哺乳动物（广义）；狗 ~ 项圈（相关）。

**④ Schema（数据库）**：规定**怎么存**。"养"被压成一个外键列，**数据库并不知道这列叫"养"**。
> 狗表(id, 名字, 品种, **主人id**)。——"主人id"藏着"养"的语义，但库本身不认识"养"。

**⑤ 本体 Ontology**：类 + **有名字的多种关系** + 公理 + 可推理。
> 类：人、狗。 关系：**养(owns)**、住在(livesIn)。 公理：一只狗至多一个主人；狗和猫不相交。 推理：若 A 养 B、B 是狗 ⟹ A 是"养狗的人"。

**⑥ 知识图谱 KG**：本体（模板）+ **塞满真实数据**。
> 模板（⑤）+ 实例：小明 —养→ 旺财；旺财 是 金毛；旺财 住在 北京。

#### 最容易卡的一句：什么叫"关系是一等公民"

对比 **④ 和 ⑤** 就懂了：

- **Schema 里**，"养"不是个东西，只是狗表里的一个 `主人id` 列——它**没有名字、没有规则**，数据库只知道"两行用一个 id 对上了"，不知道这叫"养"、更不知道"一只狗只能有一个主人"。
- **本体里**，`养(owns)` **本身就是一个有名有姓的对象**：它规定主语必须是人、宾语必须是狗（定义域/值域）、一只狗至多一个主人（约束）、还能据此推理。

> **"关系是一等公民" = 关系自己也被显式建模，而不是藏在外键里的副产品。**

一句话记住整张对比：**Schema 只回答"怎么存"；本体还回答"是什么、怎么关联、能推出什么"。**

### 项目映射

专访 1.0 现在处在"**隐性 Schema + 散落 Taxonomy**"这一层：

- 它有 `ProductState`（25+ 数组的 TS 类型）——这是 **Schema**，面向存储，关系靠字符串 id 外键隐含。
- 它有零散的 is-a 直觉（"观点/问题/决策/知识债都是认知资产"）——但这个 **Taxonomy 从未被显式写出**，于是每个数组各自为政。
- 它**没有**显式的关系类型表，也**没有**可校验的公理——所以"删除不级联""召回漏类""归属靠子串猜"这些问题反复出现。

> 诊断结论：**本体已经隐含存在于产品的概念中（认知图谱），但系统只把它实现到了 Schema 层。** 本次重构 = 把它提升到 Ontology 层。

### 动手
P0 的第一件事，就是把"概念化"显式写下来：专访 1.0 里**到底存在哪些种类的认知实体、它们之间有哪些种类的关系**。这份规范就是 §5 的产物。

## 2. 本体的构成要素（building blocks）

### 理论

任何本体都由这几类元素搭成（OWL/RDFS 的术语标在括号里）：

1. **个体 / 实例**（Individuals / Instances，OWL: `Individual`）：殊相。"我 2026-06-20 说的那句话"。
2. **类 / 概念**（Classes / Concepts，OWL: `Class`）：共相。"观点""主题"。类可有**子类**（`subClassOf`），形成 is-a 层级。
3. **属性 / 数据属性**（Attributes / Datatype Properties）：实体到字面值。`Theme.maturity = "成型"`。
4. **关系 / 对象属性**（Relations / Object Properties）：实体到实体，**带定义域 domain 和值域 range**。`belongs_to_theme: Point → Theme`。关系可有特性：传递性（transitive）、对称性、函数性（functional，即至多一个值）等。
5. **公理 / 约束**（Axioms / Constraints）：必然为真的规则。"每个观点必须有证据来源""敏感记忆不进公开召回"。
6. **规则**（Rules）：由已知推出新知。"若 A 属于主题 T 且 T 演化为 T'，则 A 与 T' 相关"。

### 项目映射

把要素逐一钉到真实代码（类型见 `src/domain/types.ts`）：

| 本体要素 | 专访 1.0 的现状 |
|---|---|
| 个体/实例 | `ProductState.points[i]`、某条 `MemoryRecord` 等——数组里的每个对象 |
| 类/概念 | 每个数组的元素类型：`Point`/`Question`/`Decision`/`KnowledgeDebt`/`Theme`/`MemoryRecord`/`DualTrackNote`… |
| 子类层级 | **缺失**（无显式父类，"认知资产"只是口头概念） |
| 属性 | 类型里的字面值字段：`Point.title/content/status`、`Theme.maturity/appearances` |
| 关系 | **散落且不统一**：`EvidenceAnchor`（内嵌结构体）、`relatedThemeIds[]`（内嵌 id 数组）、`MemoryEdge`（独立实体）—— 见 §3 |
| 公理 | **散落在 finalize/context-pack/knowledge 各处手写**，无统一表达：`clampMaturityByAppearances`、敏感过滤、HITL 门控 |
| 规则 | 基本没有显式推理（`appearances` 计数勉强算一条） |

### 动手
重构的实质就是把上表右列"缺失/散落/手写"的三类——**子类层级、统一关系、显式公理**——补成一等公民。

| 语义 | 现在的编码方式 | 代码位置 |
|---|---|---|
| **溯源**（资产 ← 来自哪一轮发言） | `EvidenceAnchor { sessionId, turnId }`，内嵌为 `evidenceAnchors?[]`/`keyQuoteAnchor`/`representativeQuoteAnchor` | types.ts:105；挂在 Point/Question/Decision/Debt/Note/Theme/Memory |

## 4. 表示层的理论谱系（核心知识地图）

这一节是"把本体论学全"的主干。每格都按 **打比方（生活类比）→ 理论 → 项目对应** 来讲——先用一个日常例子让概念落地，再给学术定义，最后钉到专访 1.0 的代码。

### 4.1 三元组与 RDF
**打比方**：一句最简单的话"小明 养 旺财"——主语「小明」、谓语「养」、宾语「旺财」。RDF 就是规定：**所有知识都拆成这种"主-谓-宾"三段式**。
**理论**：RDF（Resource Description Framework）把一切知识表示为**三元组** `(subject, predicate, object)`，例如 `(P1, belongs_to_theme, 放权)`。一堆三元组首尾相接，天然构成一张**有向标注图**（小明→养→旺财→是→金毛…）。这是知识图谱的最小公分母。
**项目对应**：我们的 `Relation { from, type, to }` 就是一条三元组。无需引入 RDF 库——三元组是**思想模型**，用 TS 对象表达即可。

### 4.2 RDFS：模式与类层级
**打比方**：RDF 让你写句子，RDFS 给句子定**语法规则**："养"这个动词，主语只能是人、宾语只能是动物——写"旺财 养 小明"就违规。
**理论**：RDFS 在 RDF 上加"模式"：`rdfs:Class`（类）、`rdfs:subClassOf`（is-a）、`rdfs:domain`/`rdfs:range`（关系的定义域/值域，即"主语/宾语必须是什么类"）。
**项目对应**：§5.2 的实体分类法 = `subClassOf`；§5.3 关系表的 domain/range 列 = `rdfs:domain/range`（如 `belongs_to_theme` 主语必须是资产、宾语必须是主题）。我们用 TS 的 discriminated union + 关系表落地，不用 RDFS 语法。

### 4.3 OWL 与描述逻辑（DL）
**打比方**：RDFS 只能定简单语法；OWL 能写**更复杂的规则**还能**自动推论**——好比你告诉系统"父亲就是男性的家长""家长关系可传递"，它能自己推出"爷爷是父亲的父亲、也是男性长辈"，不用你一条条录。**TBox / ABox** 的区分就像"**字典 vs 病历**"：TBox 是字典（定义"什么是糖尿病、什么是并发症"这些概念和规则），ABox 是具体某个人的病历（"张三患糖尿病"这些事实）。
**理论**：OWL（Web Ontology Language）建立在**描述逻辑（DL）**上——一阶逻辑的**可判定片段**（"可判定"=保证推理一定能在有限步内算完、不会死循环）。它区分 **TBox**（terminology：类与关系的公理，"概念层/字典"）与 **ABox**（assertions：个体事实，"数据层/病历"）。OWL 能表达类的不交、基数约束（"恰好 1 个"）、属性传递性、由属性推出的类成员（"有≥1条 derived_from 边的，自动算作 GroundedAsset"）。配套**推理机**（reasoner，如 HermiT、Pellet）做**蕴含计算**（entailment）：从显式规则推出隐含事实，并检查矛盾。
**项目对应（关键决策）**：**不引入 OWL/reasoner**。原因：①它为开放世界与跨系统互操作设计（见 4.4），单用户本地用不上；②它的推理为大规模、需可判定性证明的场景设计，我们的"推理"（成熟度推导、矛盾检测）用**确定性纯函数**就够，且更可控、可测、可调试。我们**借用 TBox/ABox 的思维**（把"本体规范=字典"和"实例数据=病历"分开），但用轻量手段实现。

### 4.4 开放世界 vs 封闭世界假设（OWA / CWA）
**打比方**：你问"小明有没有兄弟？"数据库里查不到——
- **封闭世界（CWA）**回答："**没有**"（查不到就是没有，像公司员工表里搜不到这人就是没这员工）。
- **开放世界（OWA）**回答："**不知道**"（只是我没记录，不代表现实里没有，像维基百科没写不代表事实不存在）。
**理论**：RDF/OWL 默认 **OWA**——因为 Web 知识天生不完整，"没说" ≠ "为假"。数据库与大多数编程默认 **CWA**——"库里没有 = 不存在"。另有**唯一名假设 UNA**：OWL 不默认"不同的名字指不同的东西"（"鲁迅"和"周树人"可能是同一人），数据库默认假设。
**项目对应**：专访 1.0 是单用户、数据自包含的——**CWA 才是对的**。"用户没有指向某主题的观点"就该当"没有"，而非"未知"。所以我们的公理校验是**封闭世界的确定性检查**（"这条蒸馏没有任何 `derived_from` 边 → 直接判违例"），正好与 OWL 的 OWA 相反。**搞懂 OWA/CWA 的差异，就懂了为什么本项目不该套 OWL。**

### 4.5 上层本体（Upper / Foundational Ontologies）
**打比方**：每个行业建模型都要重新定义"东西""事件""时间"太浪费，于是有人先做好一套**通用底座**（像盖楼前先打好的标准地基），各领域本体往上接就行。其中最有用的一个区分是 **"对象 vs 事件"**：一个**人**（对象，会一直存在、状态会变）和一场**会议**（事件，发生完就成历史、不会再变）——这俩本质不同。
**理论**：上层本体是通用、领域无关的顶层类体系，给领域本体共享骨架。代表：
- **BFO**（Basic Formal Ontology）：核心二分 **continuant（持续体，在时间中保持同一性）vs occurrent（发生体，在时间中展开的过程/事件）**。
- **DOLCE**：endurant/perdurant/quality/abstract 四分，偏认知与语言。
- **SUMO**：大而全的通用本体。
**项目对应**：BFO 的 continuant/occurrent 二分**精准切中**本系统：
- **`InterviewTurn`（轮次）= occurrent**：一个发生在具体时刻的言说**事件**，是不可变的历史证据。
- **`Point`/`Theme`/`MemoryRecord` = continuant**：在时间中持续、可更新状态、保持同一性的**认知对象**。
这个区分立刻给出设计启示：occurrent（Turn）应当**不可变、只追加**（事实就是事实），continuant（资产）才有"状态流转/更新"。本系统把 Turn 放冷层只追加、资产可改——**其实已经暗合 BFO，只是没自觉**。

### 4.6 OntoClean：清洗 is-a 的方法论
**打比方**：有人说"学生是一种人"——对的；但说"学生是一种身份证号"就荒谬。怎么系统性地揪出这种错误的"是一种"？OntoClean 给了一套**体检指标**。最有用的一条叫**刚性**：问"这个标签会不会变？"——"人"终生不变（刚性），"学生"会毕业（**反刚性**）。规则：**会变的类，不能当不变的类的父类**。
**理论**：Guarino & Welty 提出，用一组**元属性**给类打标，检验 `subClassOf` 是否站得住：
- **刚性 Rigidity**：实例是否**必然**属于该类、终生不变？"人"是刚性的；"学生"是**反刚性**的（会毕业）。
- **同一性 Identity**：该类是否提供"判断两个实例是否同一"的准则？
- **统一性 Unity**：实例是否是一个有明确边界的整体？
- **依赖 Dependence**：该类的实例是否必依赖另一类实例存在？
规则：**反刚性的类不能做刚性类的父类**等，用来揪出错误的 is-a。
**项目对应（一个真问题）**：能说 `Theme subClassOf Note` 吗？用刚性检验——一条 `Note` 永远是 Note（刚性），而 `Theme` 是跨多条资产**涌现**出来的聚合轴，它的"成员"会增减、成熟度会变（反刚性/可演化）。结论：**Theme 不是 Note 的父类，而是一个独立的、聚合性的 Axis 类**。OntoClean 帮我们避免把"聚合轴"误塞进资产层级——这正是 §5.2 把 `Axis` 单列的理论依据。

### 4.7 部分整体论（Mereology）
**打比方**：注意两句话的天壤之别——"轮子是**一种**汽车"（错，is-a）vs "轮子是汽车的**一部分**"（对，part-of）。前者讲"是不是同类"，后者讲"是不是零件"。初学者最常把这俩搞混。
**理论**：Mereology 研究"部分–整体"关系（parthood）：真部分、传递性（A 是 B 的部分、B 是 C 的部分 ⇒ A 是 C 的部分）、整体的**涌现性质**（整体有而单个部分没有的属性）。part-of 与 is-a 是**两种不同关系**。
**项目对应**：
- `Session ⊐ Turns`：一次专访由多个轮次**组成**（part-of，非 is-a）。
- `Theme` 作为**聚合整体**：由指向它的多条资产"组成"，其 `maturity` 是**涌现属性**（单条资产没有成熟度，聚合才有）——这解释了为什么 `clampMaturityByAppearances`（成熟度由成员数封顶）在理论上是对的。

### 4.8 溯源本体 PROV-O
**打比方**：超市一盒鸡蛋上的**溯源码**——扫一下能看到"哪个农场（来源）、哪天产的（活动）、哪家公司负责（归因）"。PROV-O 就是把"任何信息的来龙去脉"标准化成这种可追查的结构。
**理论**：W3C 标准本体，专门表示"**这东西从哪来、谁负责、怎么生成**"。三个核心类 **Entity / Activity / Agent**，三条核心关系 `wasGeneratedBy`（实体由活动生成）、`wasDerivedFrom`（实体派生自实体）、`wasAttributedTo`（实体归因于主体）。
**项目对应（高价值）**：专访 1.0 的"证据链"本质就是 PROV-O：
- `Point wasDerivedFrom Turn` ← 这正是 `EvidenceAnchor`！
- "这条记忆是 LLM 抽的还是用户确认的" ← `wasAttributedTo` 一个 Agent（LLM / 用户）。
我们的 `Provenance { origin, sessionId, turnId, confidence }`（§5.1）就是 PROV-O 的轻量化。**把散落的 `EvidenceAnchor` + `sourceType` + HITL 状态统一成 Provenance，等于给系统装上标准溯源本体**——审查里"敏感内容不进召回""HITL 不能把推断当事实"都变成对 `provenance.origin` 的统一过滤。

### 4.9 校验：SHACL vs 推理
**打比方**：填表单时——**红框报错"手机号必须 11 位"**（这是 SHACL：检查你填的合不合规，不合就拦）；而**输入框自动补全/联想**（这是 OWL 推理：根据已知推出新内容）。两者方向相反：一个**挑错**，一个**生成**。
**理论**：SHACL（Shapes Constraint Language）是 W3C 的**约束校验**语言——定义"形状"（节点必须满足的条件）去**验证**图，违反即报错。它与 OWL 推理是**不同范式**：OWL（OWA）"推出新事实"，SHACL（CWA）"检查已有数据是否合规"。本项目的公理校验天然属于 SHACL 式。
**项目对应**：§6 的公理引擎 `axioms.check(state)` = SHACL 式校验器（封闭世界、报违例），而不是 OWL 推理机。

## 5. 目标本体设计（把理论落到本系统）

### 5.1 上层 meta-model（= 个体/关系/PROV-O 的落地）

```ts
type EntityKind =
  | 'session' | 'turn'                          // occurrent / 容器
  | 'note' | 'point' | 'decision' | 'debt'      // Distillation
  | 'question'                                  // Inquiry
  | 'theme'                                     // Axis（聚合）
  | 'memory' | 'memory_candidate'               // Memory
  | 'material' | 'rag_chunk' | 'search_brief';  // External

// 个体的统一外壳 + 强类型内核（避免 attributes 退化成 any）
type EntityNode =
  | { id: string; kind: 'point';  attributes: Point;        createdAt: string; updatedAt: string }
  | { id: string; kind: 'theme';  attributes: Theme;        createdAt: string; updatedAt: string }
  | { id: string; kind: 'memory'; attributes: MemoryRecord; createdAt: string; updatedAt: string }
  // … 每个 kind 一支，attributes 沿用现有类型定义
  ;

// 一等关系（= RDF 三元组 + PROV-O 溯源）
interface Relation {
  id: string;
  from: string; to: string;       // 三元组的 subject / object
  type: RelationType;             // 三元组的 predicate（见 5.3）
  provenance?: Provenance;        // PROV-O：这条事实从哪来
  weight?: number;                // 召回排序用
  createdAt: string;
}

// PROV-O 轻量化：统一溯源 + 来源类型 + 可信度
interface Provenance {
  origin: 'llm_extracted' | 'user_confirmed' | 'heuristic' | 'imported' | 'seed'; // wasAttributedTo
  sessionId?: string; turnId?: string;   // wasDerivedFrom 的目标证据
  confidence?: number;
}
```

> 理论锚点：`EntityNode`=个体（§2）、`Relation`=对象属性/三元组（§4.1）、`Provenance`=PROV-O（§4.8）、强类型 union=避免 OWL 那种无类型灵活性带来的失控（我们要 CWA 的严格，§4.4）。

### 5.2 实体分类法（= subClassOf 层级，经 OntoClean 检验）

```
CognitiveEntity（认知实体：可溯源、可归类、可治理）
├── Utterance     言说类(occurrent, 不可变)   → Turn
├── Distillation  蒸馏类(continuant)           → Note / Point / Decision / Debt
├── Inquiry       追问类(continuant)           → Question
├── Axis          主轴类(聚合, 反刚性)         → Theme
├── Memory        记忆类(continuant)           → MemoryRecord / Candidate / Correction
└── External      外部类                       → ImportSource / RagChunk / SearchBrief
```

理论锚点：父类划分用了 §4.5 BFO（Utterance=occurrent）+ §4.6 OntoClean（Axis 反刚性，单列不塞进资产）。父类带来**统一能力**：治理（按父类做 export/purge/敏感过滤）、召回（统一遍历"指向某主题的所有 Distillation/Inquiry/Memory"）、证据（所有 CognitiveEntity 都能 derived_from 某 Utterance）。

### 5.3 关系类型表（= object properties，带 domain/range/cardinality/特性）

| RelationType | domain → range | 基数 | 特性 | 取代现状 | 理论 |
|---|---|---|---|---|---|
| `derived_from` | CognitiveEntity → Turn | N:M | —— | `EvidenceAnchor` | PROV-O wasDerivedFrom |
| `belongs_to_theme` | Distillation/Inquiry → Theme | N:M | —— | `relatedThemeIds[]` | RDFS domain/range |
| `about_theme` | Memory → Theme | N:M | —— | `MemoryEdge` | 同上（统一掉双轨） |
| `promoted_from` | Question → Note | N:1 | functional | 仅文案；**schema `reserved-no-consumer`**（见 `docs/runbooks/reserved-graph-edges.md` · `002_relations.surql`） | 函数性属性 |
| `part_of` | Turn → Session | N:1 | transitive | `sessionId` | Mereology（§4.7） |
| `derives` | ImportSource → RagChunk → KnowledgeChunk | 1:N | transitive | `sourceId` | 派生链 |
| `corrects` | MemoryCorrection → MemoryRecord | N:1 | —— | 隐式；**schema `reserved-no-consumer`**（修正走实体，非此边） | —— |
| `contradicts` | Point ↔ Point | N:M | **symmetric** | 无（**新能力**） | 对称属性 |
| `evolves_into` | Theme(t) → Theme(t+1) | 1:1 | —— | `appearances` | 时序演化 |

最后两行是本体化**新解锁**的认知能力（关系一等化后才可能）：矛盾检测、主题演化时间线。

### 5.4 公理（= TBox 约束 / SHACL 形状，封闭世界）

| 公理 | 内容 | 现状（散落处） | 理论 |
|---|---|---|---|
| A1 | 每个 Distillation ≥1 条 `derived_from`（无溯源=幻觉，拒收/标记） | finalize 各处 | SHACL minCount |
| A2 | `Theme.maturity ≤ f(belongs_to_theme 边数)` | `clampMaturityByAppearances` | 涌现属性（§4.7） |
| A3 | `provenance.origin='llm_extracted'` 未经 `user_confirmed` 不得呈现为"事实" | HITL 各链路 | PROV-O 归因门控 |
| A4 | `sensitivity='sensitive'` 的 Memory 不产生进入 chat 索引的派生边（除非 policy 开） | knowledge 召回 | 约束 |
| A5 | 删除任一 EntityNode → 出入边级联删除（根除孤儿） | **当前缺失** | 引用完整性 |

> 关键洞察：A1–A4 **现在都是散落在 finalize/context-pack/knowledge 里、各写一遍、容易漏的逻辑**——系统审查里大半 bug 是"某条链路漏了某条规则"。**公理化 = 写一处，校验器统一兜底。** A5 直接消灭"删除孤儿"这一类跨库一致性问题。

## 6. 推理与一致性（轻量版 entailment）

### 理论
**蕴含/推理**（entailment）：从显式知识推出隐含知识。OWL 用描述逻辑推理机做（OWA，§4.3/4.4）；但推理不必那么重——**确定性规则 + 图遍历**也是推理，且封闭世界下更适合应用系统。

### 项目映射 + 动手
推理层 = 一组确定性纯函数，在 `OntologyGraph` 上跑（**不引入 reasoner**）：
- **传递闭包**：`part_of`/`evolves_into` 的传递展开 → 时间线自动连。
- **矛盾检测**：同主题下内容/状态对立的两个 Point → 生成 `contradicts` 边 + 提示复盘。
- **成熟度推导**：A2 作为推导规则。
- **召回**：从 query 实体出发的加权邻域遍历，替代 `collectRelevantMemories` 的手工列举（根除"漏 decisions"类 bug）。
- **一致性校验**：`axioms.check(state)` 跑 A1–A5（SHACL 式，§4.9），违例记审计、必要时拦截。

架构上，`OntologyGraph` 是**从 `ProductState` 投影出的内存索引**（像现在的 knowledge_index），**存储层不动**、纯函数范式不动——这与 SurrealDB 评估同一条纪律：本体是**领域模型层**的事，与持久化正交。

## 8. 收益 / 成本 / 风险 / 决策

**收益**（确定性排序）：①根治一类 bug（孤儿/删除不级联/召回漏类/归属靠猜/HITL 漏规则——同一根因）；②边际成本下降（加资产/关系/召回从"改 N 处"变"加一个 kind/RelationType"）；③解锁产品叙事（矛盾检测、主题演化、认知图谱可视化）；④LLM 更可控（受控三元组）；⑤**你系统学完一遍本体论且每块都落过地**。

**成本**：P0–P3 渐进改写域层部分函数与测试（适配器并存，非冻结式重写）；P4 才是大重写（不默认做）；一次性认知成本（"按图思考"）。

**风险与缓解**：新旧边并存歧义 → 单向投影+写时双写、P2 末删老字段；过度抽象成 any → 强类型 union 内核；推理变黑箱 → 只允许确定性纯函数+公理显式列举；投机做 P4 → 明确标可选。

**决策**：
1. **现在做 P0**（写规范，零风险）。
2. **P1–P3 作为"认知图谱化"主线**渐进推进，优先级在"新功能"与"修 bug"之间（因为顺手修一批根因 bug）。
3. **不上 L3 语义网**（OWL/RDF 库/SPARQL/reasoner）——规模不匹配、CWA 才对（§4.4），纯增风险。
4. **存储层不动**；P4 默认不做。

**何时该重估升级到 L3**（满足任一）：走向多用户/跨系统互操作；需对接外部 RDF 知识库；推理超出确定性纯函数表达力；实体规模到十万+。均不满足 → L2 务实本体是终点。

### 9.2 端到端示例：一轮专访如何变成本体

用户某轮说："我决定把招聘权下放给团队，但我担心失控。"

**现状**：finalize → 一条 `Decision` + 一条 `Point` → 各塞数组 → `attributeThemeIds` 子串猜"放权"主题 → `relatedThemeIds` 写 id → `EvidenceAnchor` 内嵌。四处逻辑、三套边。

**本体化后**：finalize 让 LLM 直接产出**受控三元组**（schema 即 §5.3 关系表）：

```
(decision:D1 "招聘权下放") --derived_from--> (turn:T7)   prov{ origin: llm_extracted, turnId: T7 }
(point:P1   "担心失控")    --derived_from--> (turn:T7)
(D1) --belongs_to_theme--> (theme:放权)
(P1) --belongs_to_theme--> (theme:放权)
(P1) --contradicts-->      (point:P0 "倾向亲自把关")     ← 推理层检出张力（symmetric）
```

下游全部按本体遍历，一处建模处处一致：
- **召回**：`neighbors(放权, 'belongs_to_theme')` 一次拿全（不会漏 decision）。
- **溯源**：`provenanceOf(D1)` 直达 T7（统一，不分内嵌字段）—— PROV-O。
- **治理**：删 session → A5 级联删 T7 及其所有入边（无孤儿）。
- **HITL/敏感**：A3/A4 对 `provenance.origin` 统一门控。
- **新能力**：`contradicts` 触发"认知张力"提示；`evolves_into` 串出主题演化时间线。

> 这就是本体论重构的价值：**把"隐性、散落、各处手写"的领域知识，提升为"显式、统一、可推理、可校验"的一等本体。** 学每一块理论，都在这张图上落一次地。
