## 1. 三元组：知识的"原子"

### 打比方
小学造句：**谁、干什么、对谁**。"小明 养 旺财"。任何一条信息，几乎都能压成这种**主-谓-宾**三段。三元组就是把这件事变成铁律：**所有知识，一律拆成 `(主语, 谓语, 宾语)`。**

### 理论
三元组 `(subject, predicate, object)` 是 RDF 的最小单位，也是知识图谱的"原子"。它的威力在于**极简却万能**：

- 描述属性：`(旺财, 品种, 金毛)` —— 宾语是个字面值。
- 描述关系：`(小明, 养, 旺财)` —— 宾语是另一个实体。
- 描述关于关系的事：把整条三元组当主语再描述（"小明养旺财 这件事 发生于 2026"）——这叫**具体化 reification**，是 N 元关系的处理手段（后续 ODP 篇细讲）。

为什么三段就够？因为任何"N 个东西的复杂关系"都能拆成多条二元关系。"小明在北京用支付宝给旺财买了狗粮"→ 拆成若干条 `(买狗粮事件, 买家, 小明)`、`(买狗粮事件, 地点, 北京)`、`(买狗粮事件, 支付, 支付宝)`…… 这正是 reification 的用法。

### 项目对应
01 §5.1 定义的 `Relation` 就是一条三元组：

```ts
interface Relation {
  from: string;   // subject —— 某个 EntityNode.id
  type: RelationType; // predicate —— belongs_to_theme / derived_from / ...
  to: string;     // object —— 另一个 EntityNode.id
  provenance?: Provenance; // 额外挂在这条边上的"溯源"(关于这条事实的事实)
}
```

`(P1, belongs_to_theme, 放权)` = `{ from: "P1", type: "belongs_to_theme", to: "theme-放权" }`。**不引入任何 RDF 库**——三元组是思想模型，一个 TS 对象就是它。

### 动手
P1 的类型定义里，`Relation` 已经是三元组形态。第一步只是把它**当成一等数据**存进 `state.relations: Relation[]`（而不是继续把关系塞进各实体的内嵌字段）。

## 2. 三元组堆成图

### 打比方
一条三元组是一根**箭头**：`小明 —养→ 旺财`。很多条箭头首尾相接，就成了一张**关系网**：`小明 —养→ 旺财 —品种→ 金毛`，`小明 —住在→ 北京`。这张网就是图（graph）。

### 理论
- **节点（node/vertex）= 实体**，**边（edge）= 一条三元组**，边有**方向**（from→to）和**类型**（predicate）。所以知识图谱是一张 **有向、带类型标注的多重图**（multigraph：两个节点间可有多条不同类型的边）。
- 图天然适合知识，因为现实里的关联就是网状的，而**表格（Schema）是把网硬拍平成行列**——一旦关系多向、多类型，表格就要靠一堆外键和 join 勉强模拟，语义还丢了（回看 01 §1 的"狗/主人"④⑤对比）。

### 项目对应
把专访 1.0 的认知资产看成图：

```
(turn:T7) ←─derived_from─ (decision:D1)
                              │ belongs_to_theme
                              ▼
                          (theme:放权)
                              ▲ belongs_to_theme
                              │
(turn:T7) ←─derived_from─ (point:P1) ─contradicts─ (point:P0)
```

同一个 `theme:放权` 节点，被 D1、P1 多条边指入——**这正是当前用 `relatedThemeIds[]`（散在各资产里）很难高效反查"谁指向放权"的原因**：信息被拆散在各数组里，没有"以主题为中心看入边"的视角。图把它天然补上。

## 3. 图怎么存：邻接表 vs 邻接矩阵

### 打比方
记录"谁认识谁"：
- **邻接矩阵**：拉一张 N×N 大表格，每格填 0/1。人少时直观，人多时**绝大多数格子是 0**（你不认识地球上 99.99% 的人），极度浪费。
- **邻接表**：每个人只记一个"我认识的人"小名单。**稀疏时省得多**，查"我认识谁"一步到位。

### 理论
- **邻接矩阵** `M[i][j]`：空间 O(N²)，查"i 和 j 是否相连"O(1)，但稀疏图浪费巨大。
- **邻接表**：每个节点挂一个邻居列表，空间 O(N+E)，查"某节点的邻居"O(度数)。知识图谱是**稀疏图**（每个实体只和少数实体相关），**邻接表是标准选择**。
- 工程上常**双向索引**：既存"从某节点出发的边"（out），也存"指向某节点的边"（in），这样"P1 属于哪些主题"和"哪些资产属于放权主题"都能 O(度数) 查到。

### 项目对应
`OntologyGraph` 就是从 `state.relations` 建的**双向邻接索引**：`outByNode: Map<id, Relation[]>` + `inByNode: Map<id, Relation[]>`。规模上专访 1.0 是数百~数千节点的稀疏图，邻接表内存索引遍历**微秒级**——这也是 01 §6"不需要数据库、内存图足够"的依据（与 SurrealDB 评估同一结论）。

## 4. 把 ProductState 投影成图

### 打比方
`OntologyGraph` 不是"另起一个新数据库"，而是像 Excel 的**数据透视表**：原始数据还在原表（`ProductState`），透视表是**按需重新组织的视图**，方便你换个角度查。换句话说，图是 `ProductState` 的**投影/索引**，不是第二份真相。

### 理论
这是关键架构决策：**单一事实源（single source of truth）仍是 `ProductState`**，`OntologyGraph` 是从它**投影**出来的内存结构。好处：①存储层不动（呼应 01 §6 / SurrealDB 评估）；②纯函数范式不变——`(state)=>state` 照旧，只是内部从"手工遍历 25 数组"换成"查图"；③图可随时从 state 重建，不存在"图和 state 不一致"的双写难题（除非引入持久化图，P4 才考虑）。

### 项目对应：投影怎么做
两步：**节点投影** + **边投影**。

```ts
function projectGraph(state: ProductState): OntologyGraph {
  const nodes = new Map<string, EntityNode>();
  // ① 节点：每个实体数组 → EntityNode（kind + 内核 attributes）
  for (const p of state.points)  nodes.set(p.id, { id: p.id, kind: 'point',  attributes: p, createdAt: p.createdAt ?? '', updatedAt: p.updatedAt ?? '' });
  for (const t of state.themes)  nodes.set(t.id, { id: t.id, kind: 'theme',  attributes: t, createdAt: t.createdAt ?? '', updatedAt: t.updatedAt ?? '' });
  for (const m of state.memoryRecords) nodes.set(m.id, { id: m.id, kind: 'memory', attributes: m, createdAt: m.createdAt ?? '', updatedAt: m.updatedAt ?? '' });
  // … 其余 kind 同理（note/decision/debt/question/session/turn/material）

  // ② 边：见 §6 适配器——把三套旧编码 + 新 state.relations 统一成 Relation[]
  const relations = collectRelations(state);

  return buildGraph(nodes, relations);
}
```

§5 给出 `OntologyGraph` 的查询接口，§6 给出 `collectRelations`（吞三套边）。

## 5. OntologyGraph 的接口与实现草案

### 接口（域层只依赖它，不再手工遍历数组）

```ts
interface OntologyGraph {
  node(id: string): EntityNode | undefined;
  // 出/入邻居，可按关系类型过滤。dir 默认 'out'
  neighbors(id: string, type?: RelationType, dir?: 'out' | 'in'): EntityNode[];
  relationsOf(id: string, dir?: 'out' | 'in'): Relation[];
  // 沿 derived_from 回溯到 Turn，拿这条实体的全部证据来源（PROV-O）
  provenanceOf(id: string): Provenance[];
}
```

### 内存实现（邻接表 + 双向索引）

```ts
function buildGraph(nodes: Map<string, EntityNode>, relations: Relation[]): OntologyGraph {
  const out = new Map<string, Relation[]>();
  const inn = new Map<string, Relation[]>();
  for (const r of relations) {
    (out.get(r.from) ?? out.set(r.from, []).get(r.from)!).push(r);
    (inn.get(r.to)   ?? inn.set(r.to, []).get(r.to)!).push(r);
  }
  const pick = (rels: Relation[], type?: RelationType) =>
    type ? rels.filter((r) => r.type === type) : rels;

  return {
    node: (id) => nodes.get(id),
    relationsOf: (id, dir = 'out') => (dir === 'out' ? out : inn).get(id) ?? [],
    neighbors(id, type, dir = 'out') {
      const rels = pick((dir === 'out' ? out : inn).get(id) ?? [], type);
      return rels
        .map((r) => nodes.get(dir === 'out' ? r.to : r.from))
        .filter((n): n is EntityNode => !!n);
    },
    provenanceOf(id) {
      // 直接来源：这条实体自身边上的 provenance + 它 derived_from 的 Turn
      const own = (out.get(id) ?? []).filter((r) => r.type === 'derived_from');
      return own.map((r) => r.provenance ?? { origin: 'heuristic', turnId: r.to });
    }
  };
}
```

> 教学点：`neighbors(放权主题, 'belongs_to_theme', 'in')` 一行就回答"哪些资产属于放权主题"——这正是当前 `collectRelevantMemories` 要手工列举 notes/points/.../themes 才能凑齐的事（还漏过 decisions）。图把"加一种资产、召回自动覆盖"变成现实。

## 6. P1 适配器：吞掉三套边编码

### 为什么需要适配器
01 §3 诊断出：**同一类关系被四套方式编码**（`EvidenceAnchor` 内嵌、`relatedThemeIds[]` 内嵌、`MemoryEdge` 独立、谱系纯文案）。P1 不可能一次性删光旧字段（会破坏一堆读取点），所以策略是：

> **读时统一投影，写时逐步迁移。** 先让 `collectRelations` 把"新 `state.relations` + 三套旧编码"都翻译成统一的 `Relation[]`，下游只认 `Relation`。旧字段暂时保留、并存，等 P2 下游全切到图后再删。

### 实现：四套 → 一套

```ts
function collectRelations(state: ProductState): Relation[] {
  const rels: Relation[] = [...(state.relations ?? [])]; // 新模型已有的边

  // ① EvidenceAnchor → derived_from（溯源）。挂在各资产上的 anchor 投影成边。
  const anchorEdges = (entityId: string, anchors?: EvidenceAnchor[]) =>
    (anchors ?? []).forEach((a) =>
      rels.push({
        id: `der:${entityId}:${a.sessionId}:${a.turnId}`,
        from: entityId, to: `${a.sessionId}#${a.turnId}`, type: 'derived_from',
        provenance: { origin: 'llm_extracted', sessionId: a.sessionId, turnId: a.turnId },
        createdAt: ''
      }));
  for (const p of state.points)   anchorEdges(p.id, p.evidenceAnchors);
  for (const d of state.decisions) anchorEdges(d.id, d.evidenceAnchors);
  // … note.keyQuoteAnchor / theme.representativeQuoteAnchor 同理

  // ② relatedThemeIds[] → belongs_to_theme（归类）
  const themeEdges = (id: string, themeIds?: string[]) =>
    (themeIds ?? []).forEach((tid) =>
      rels.push({ id: `bt:${id}:${tid}`, from: id, to: tid, type: 'belongs_to_theme', createdAt: '' }));
  for (const p of state.points)    themeEdges(p.id, p.relatedThemeIds);
  for (const q of state.questions) themeEdges(q.id, q.relatedThemeIds);
  // … decisions / debts / notes 同理

  // ③ MemoryEdge → about_theme（记忆挂主题）。把独立实体并入统一边模型。
  for (const e of state.memoryEdges)
    rels.push({ id: e.id ?? `at:${e.fromMemoryRecordId}:${e.themeId}`,
      from: e.fromMemoryRecordId, to: e.themeId, type: 'about_theme', createdAt: e.createdAt ?? '' });

  return rels;
}
```

### 这一步直接修掉的审查 bug
- **删除孤儿**：边一旦统一，删节点时 `relationsOf(id,'out'/'in')` 能一次拿到全部出入边 → 级联删（公理 A5）。
- **MemoryEdge 与 relatedThemeIds 双轨**：投影后都是边，主题聚合只需 `neighbors(theme, _, 'in')`，不再两套逻辑。
- **召回漏 decisions**：召回改成图遍历，新增 kind 自动覆盖。

## 小结
- 三元组是知识的原子（主-谓-宾），一个 TS 对象即可，不用 RDF 库。
- 三元组堆成**有向带类型图**；稀疏图用**邻接表 + 双向索引**存，内存微秒级。
- `OntologyGraph` 是 `ProductState` 的**投影/索引**，不是新数据库——存储与纯函数范式都不动。
- **适配器 `collectRelations`** 把四套旧边编码统一成 `Relation`，是 P1 的核心动作，直接修掉删除孤儿/双轨/召回漏类。
