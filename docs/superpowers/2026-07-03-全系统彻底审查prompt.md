# 专访 1.0 · 全系统彻底审查 Prompt（v2）

> 用法：开一个新 session，把「Prompt 正文」整段发给审查 agent。适合多 agent 并行，也适合单 agent 分阶段执行。
> v2 的核心变化：旧审查报告只作为**回归种子**，不能作为当前事实；所有发现必须重新验当前代码、当前接线、当前运行结果。

---

## Prompt 正文（从这里开始复制）

你要对本仓库（`专访 1.0`，语音专访式认知产品：React 前端 + Fastify API + 域层纯函数 + SQLite/SurrealDB/dual-surreal 持久层 + LLM 智能层 + 语音链路）做一次**全系统彻底审查**。

目标不是复述旧报告，而是回答当前代码在当前配置下是否真实可靠：架构是否成立，用户旅程是否可达，数据是否能被正确生产、存储、消费、演化、删除，失败是否可见，隐私是否闭合，前后端契约是否一致。

### 0. 基本纪律

1. **当前运行时真相优先**：以当前文件、当前 `package.json` 脚本、当前 `.env.example` / `.env.production.example` / 实际注册路由为准。README、历史报告、注释、记忆只能当线索。
2. **历史报告只当回归种子**：必须阅读 `docs/superpowers/2026-07-03-全系统彻底审查报告.md`、`docs/superpowers/2026-07-03-全量修复落地.md`、`docs/superpowers/2026-07-04-回归审查报告-B12修复.md`，但每条旧问题要重新判定为：`已闭合` / `回归` / `变形未闭合` / `不再适用` / `无法验证`。
3. **CodeGraph 优先，但不迷信**：若仓库根目录有 `.codegraph/`，先用 `codegraph explore` / `codegraph node` 建图；判定“死代码、未消费、无调用”前必须再用文本搜索或运行证据复核。若 CodeGraph 命中 `.claude/worktrees/*`、历史 worktree、备份目录或旧快照，默认只当噪声，不得当成当前产品代码。
4. **测试绿不等于生产可达**：单测绕过包装器、能力注入、env 档位、auth、前端入口时，不能证明用户真的可用。每个关键能力都要追到生产路径。
5. **fail-safe 是重点审计对象**：降级本身不是 bug；无信号、假成功、语义错、掩盖上游错误才是 bug。
6. **不泄露 secret**：不要打印 `.env.local` 的值、token、cookie、私钥、支付数据。查版本必须运行二进制或包的 version 命令，不读 vendor/旧源码快照。
7. **只读优先**：审查默认不改业务代码、不删数据、不 reset、不 clean、不 push。需要真实运行实验时，先说明是否会写入本地数据库；破坏性实验只允许在临时副本或显式测试库中做。

### 1. 发现准入标准

进入最终报告的每条发现必须具备：

- `file:line` 或命令输出证据。
- 触发条件：什么配置、输入、状态或时序会触发。
- 失败场景：用户或系统会看到什么错误结果。
- 影响面：数据丢失、隐私泄漏、不可达、假成功、性能墙、维护风险等。
- 复现方式：单测、API 脚本、UI 步骤、运行日志，或说明当前只能静态推理。
- 反驳与回应：写出“它可能不是问题”的理由，再说明为什么仍成立或降级为疑点。

证据等级：

- `CONFIRMED`：已用测试、API、真实运行或最小脚本复现。
- `CODE-CONFIRMED`：当前代码路径闭合，file:line 齐，但未实际运行。
- `PLAUSIBLE`：静态推理强，但缺运行前置或时间不足。
- `REGRESSION-SEED`：来自旧报告，还未被当前证据确认；不得当作最终发现。

严重度：

- `P0`：确定性数据丢失、隐私泄漏、核心写入楔死、认证绕过、核心旅程不可用。
- `P1`：高概率丢数据/假成功/核心能力生产不可达/长期静默腐化。
- `P2`：重要业务语义错、状态机闭环断、降级信号不完整、运维恢复风险。
- `P3`：低风险缺口、可维护性风险、测试盲区、文案/可观测性小缺陷。

### 2. 阶段 0：当前能力地图

先产出一张“当前系统真实能力地图”，之后所有判断以它为基准：

1. **入口地图**：实际注册的 API 路由、前端视图入口、语音/WS/WebRTC/LiveKit 入口、脚本入口。
2. **数据地图**：`ProductState` 各数组、冷层 raw material、audio、knowledge index、SurrealDB 图边与 `state_meta`。
3. **持久层档位矩阵**：`PRODUCT_STORE` / `PRODUCT_STATE_DB_PATH` / sqlite / dual / dual-surreal / surreal / memory 的真实能力差异。
4. **能力注入矩阵**：LLM、embedding、search、TTS、ASR、native recall、knowledge reindex、write gate、budget guard 在每条路由中的接线。
5. **前后端契约地图**：`src/api/productApi.ts` 每个方法对应的后端 route、response shape、错误码语义、前端消费点。
6. **运行与验证地图**：当前 `package.json` 脚本、测试目录、Playwright 配置、dev 启动路径。不要硬编码历史 passed 数。

### 3. 阶段 1：历史问题回归矩阵

把 2026-07-03 与 2026-07-04 报告中的问题按批次重跑一遍，不要求全文照搬，但必须覆盖这些类别：

- P0 持久化确定性失败家族：非法枚举/非法 string/array、同事务级联、悬空引用、图审计。
- reset / purge / import / export / restore：热层、冷层、audio、knowledge index 是否一致，失败路径是否原子。
- autosave、revision、409、adoptServerState：前端本地态和服务端权威态是否还会互相覆盖。
- write gate、长写、scheduler、auto-run、memory consolidate：并发与强放窗口是否仍会覆盖用户写入。
- LLM budget、embedding provider、重嵌、knowledge rebuild：预算、降级、epoch/陈旧任务保护是否闭合。
- 语音链路：TTL、interrupt、ASR/TTS 断连、录音上传、doNotSave、WS 鉴权、错误回收。
- 安全隐私：auth、Origin/CSRF、URL sink、prompt 注入清洗、日志敏感内容、生产 profile 护栏。
- 产品可达性：历史“死端点/幽灵枚举/复盘闭环/记忆编辑/playbook revert”等是否真的变成可用产品能力。

输出一个矩阵：

`旧问题/批次 | 当前状态 | 当前证据 | 是否需要新 finding`

### 4. 阶段 2：九维全系统审查

#### A. 架构与分层

- 域层是否仍保持同步纯函数；是否出现 I/O、Promise、repo、provider 穿透。
- 路由是否绕过域函数手写状态，导致 invariants 失效。
- 包装器、工厂、能力注入是否透传可选能力。
- LLM budget、request timeout、write serialization、knowledge reindex 是否覆盖所有入口。

#### B. 用户旅程与业务流程

按用户能走的旅程端到端检查：

1. 文本访谈：创建、轮次、控制、结束、归档、复盘。
2. 语音访谈：连接、ASR、TTS、打断、断连、录音、结束。
3. 记忆治理：候选、批准、拒绝、编辑、撤销、整理、召回。
4. 资产治理：观点、决策、债务、问题、主题、状态迁移。
5. 外部调研：创建、刷新、盯梢、auto-run、失败降级。
6. 导入资料、RAG/chat、引用跳转、知识索引。
7. 播客生成、音频生命周期、过期链接。
8. 月/年复盘、雷达、决策回顾闭环。
9. 隐私：reset、purge、export、import、doNotSave。
10. 配置与运维：health、capabilities、playbook、migration、rebuild。

每步问：入口在哪？前置条件谁保证？失败用户看见什么？能否重放/双击？并发写入会怎样？状态值谁生产谁消费？

#### C. 数据生命周期

对每个实体建账本：

- 生产：谁创建，字段是否完整，id 和枚举是否合法。
- 存储：TypeScript 类型、SQLite/Surreal schema、blob/rest 字段是否双写发散。
- 消费：域层、SQL/Surreal 查询、前端展示、LLM prompt、RAG/recall 的过滤口径是否一致。
- 演化：AI 推断是否会覆盖用户确认；状态迁移是否有守卫。
- 删除：级联、索引、冷层、audio、图边、导出残留是否一致；删除后导入是否会重引入悬空引用。

重点找：写而无读、读而无写、双写发散、断链、无限增长表、retention 缺失、影子真相。

#### D. 一致性与不变量

- `checkAxioms` 覆盖哪些跨实体约束，漏哪些。
- 图边投影链：软链 → edge mapper → persist diff → graph audit 是否闭合。
- revision 全链：服务端 bump → route response → 前端 adopt → PUT → 409 处理。
- 公理对撞：append-only、级联删除、冷层 offload、diff baseline、write gate、budget、reindex epoch、demo seed、import/export 之间两两是否冲突。

#### E. 降级、失败与观测

搜索并分类所有 `catch` / `fallback` / `degraded` / `warn` / `fail-safe`：

- 触发条件是否明确。
- 降级是否有日志、health、UI notice 或 response 字段。
- 降级后语义是否仍正确。
- 是否制造假成功。
- 是否会让用户以为已保存、已删除、已导入、已归档。

#### F. 安全与隐私

- auth 和 Origin/CSRF 在生产、本地、反代下是否 fail-closed。
- `/api/health`、静态文件、WS、媒体 URL、`?token=` 是否有旁路。
- 外部文本进入 prompt 前是否统一清洗：导入资料、搜索结果、ASR、用户粘贴、网页标题。
- 敏感数据在存储、RAG/chat、recall provenance、导出、日志、错误响应中是否一致隔离。
- secret 是否可能出现在日志、错误体、report、导出包。

#### G. 并发与时序

- 长写是否超过 write gate 上限；释放路径是否覆盖异常、流式、连接断开。
- auto-run/scheduler/rebuild/background embedding 是否会与用户写互相覆盖。
- 前端 debounce PUT、route response adopt、轮询刷新、localStorage 保存是否会竞态。
- 所有 POST 是否幂等或至少有 UI 防重入。

#### H. 运维与恢复

- dev/prod 启动路径是否真实可用，health 是否反映关键依赖。
- backup/export/import/migrate/rebuild 是否有 dry-run 或失败保护。
- cold storage、knowledge index、audio、Surreal graph 是否能从备份恢复一致。
- 日志是否足够定位 persist、provider、embedding、scheduler、voice 的失败。

#### I. 前后端契约与 UI 可达性

- 每个后端 route 是否有前端入口、脚本入口或明确的集成用途；否则标为“预留/半成品/死功能”并给证据。
- 每个前端 API 方法是否处理 response shape、错误码、degraded 标志。
- 前端是否有空态、加载、错误、成功、禁用、防重入状态。
- 后端生产的数据是否在 UI 中可见，或明确只给 prompt/agent/运维使用。

### 5. 阶段 3：运行验证

按当前项目脚本选择验证，不要硬编码旧命令或旧 passed 数：

1. 最小静态验证：`npm run typecheck`。
2. 单元/集成：`npx vitest run` 或针对发现的测试文件。
3. 构建：`npm run build`。
4. 本地全栈：优先 `npm run dev:full`，再检查 `http://127.0.0.1:3210/api/health` 与 `http://127.0.0.1:3220`。
5. UI/真实旅程：需要时跑 Playwright；先确认服务已启动。
6. 不变量/运维：在安全测试库或临时副本上调用 graph consistency、import/export、rebuild、purge/reset 判别实验。

如果无法运行某项，写清原因。不能把未运行说成通过。

### 6. 定稿前的对抗复核

对每条候选发现做四次筛选：

1. 是否被当前代码已经修掉？
2. 是否只是设计决策？
3. 是否只有测试/注释中的路径，用户生产路径不可达？
4. 是否缺少触发条件或失败场景？

不能通过筛选的，放入“疑点/不建议做/需补证据”，不要列为正式 bug。

### 7. 输出格式

请写入或输出一份新报告，建议路径：

`docs/superpowers/YYYY-MM-DD-全系统再审查报告.md`

报告结构：

1. **执行摘要**：九维各一句结论，按 P0/P1/P2/P3 计数；明确本轮是否发现新 P0/P1。
2. **历史回归矩阵**：旧问题当前状态与证据。
3. **发现清单**：按严重度排序。格式：
   `P级 | 证据等级 | 维度 | 标题 | file:line | 触发条件 | 失败场景 | 复现方式 | 根因 | 修复草案 | 影响面 | 反驳与回应`
4. **覆盖证明**：已审且未发现问题的区域，用“维度 × 模块 × 证据方式”列出。
5. **不建议做清单**：属于设计决策、ROI 低、风险大或需产品决策的项。
6. **未覆盖/低置信区域**：诚实列出没有跑到的命令、旅程、环境。
7. **建议修复顺序**：P0/P1 优先，按最小闭环批次组织。

### 8. 有意设计清单（当前只作假设，允许挑战）

这些不是天然 bug，但如果当前证据显示代价权衡已变化，可以挑战：

- 域层同步纯函数 + 内存态为前端同步契约服务。
- CWA 公理引擎只报违例，不自动推新事实。
- turn 冷层 append-only，part_of 审计豁免有其溯源语义。
- fail-safe 降级为单用户本地工具保可用，但必须有信号且不假成功。
- chat 知识索引与 native rag 分工独立。
- PRODUCT_STORE 默认 sqlite，dual-surreal 是增强档位而非所有环境默认。
- localStorage 是离线/首屏缓存副本，但必须受 revision 收敛。
- demo seed 可以存在，但 reset/purge/import/export 的语义必须如实。
