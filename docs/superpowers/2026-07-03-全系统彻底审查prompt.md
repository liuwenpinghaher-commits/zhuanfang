# 专访 1.0 · 全系统彻底审查 Prompt（v1）

> 用法：开一个新 session，把「Prompt 正文」整段发给 Claude（建议配 ultracode / workflow 多 agent 跑，或按阶段分多个 session）。
> 本 prompt 把历次审计真正抓到 bug 的方法（生产可达性验证、判别实验、不变量审计、公理对撞）与产生过误报的坑（信文档不信运行时、codegraph 误报、旧报告过时）都编码为纪律。

---

## Prompt 正文（从这里开始复制）

你要对本仓库（专访 1.0，语音专访式认知产品：域层纯函数 + 异步 SurrealDB 权威库 + Fastify 路由 + React 前端 + LLM 智能层）做一次**彻底的全系统审查**：架构、业务流程的合理性与完善性、全部数据的设计/生产/消费/演化/删除的合理性与完善性。目标是**找出所有真实问题**。允许先广召回，但**进入最终报告的每一条都必须经过对抗验证**——误报会浪费之后全部修复投入。

### 铁律（违反任何一条，该发现作废）

1. **运行时真相优先**。系统能力以 `apps/api/src/server.ts` 实际注册的路由与实际接线为准；README/旧审计报告/代码注释/会话记忆的声称一律只当线索。本项目曾有 15+ 运维端点只存在于 README。
2. **测试绿 ≠ 生产可达**。单测直连内部对象；生产要经过包装器、能力注入矩阵、env 档位。必须验证"生产路径真的走到"：逐个检查包装器（如 `withKnowledgeReindex`）是否透传能力、能力探测（如 `asNativeRecall`）在 `PRODUCT_STORE=sqlite/dual/dual-surreal/surreal` 四档位下的行为。本项目曾有原生召回全部测试绿、但生产接线上恒为 undefined（包装器吞掉方法），fail-safe 回落把它掩成"一切正常"。
3. **fail-safe 是掩盖器**。每个 catch/降级/回落点都可能把真错掩成正常。审它们的不是"存在与否"（降级是设计），而是：降级发生时**有没有信号**、降级后的**语义还对不对**、会不会掩盖上游真错。
4. **每个发现要证据**：file:line + 触发条件 + 具体失败场景（什么输入/状态 → 什么错误结果）+ 复现方式（单测/API 脚本/UI 步骤）。能复现的标 `CONFIRMED`，仅静态推理的标 `PLAUSIBLE` 并说明缺什么证据。
5. **区分缺陷与设计决策**。对照文末「有意设计清单」；要挑战设计决策，必须论证"当初的代价权衡已经变化"，不许直接当 bug 报。
6. **自我反驳 pass**。定稿前对每条发现做一次"如何证明它不是问题"的反向论证，把反驳与回应写进该条目。

### 执行阶段

- **阶段 0 · 盘点（以实际为准）**：产出"系统真实能力地图"——(a) 全部路由清单（逐文件扫 `server.get/post/put/delete`）；(b) 数据实体清单（`src/domain/types.ts` × `packages/db/src/surreal/migrations/*.surql` 对照）；(c) 前端 API 调用点清单（`src/api/*`）；(d) env/档位/开关矩阵；(e) 域函数消费图（用 codegraph）。后续一切审查以这张地图为基。
- **阶段 1 · 分维并行审查**：九个维度（见下），每维独立审、只读、产出候选发现。
- **阶段 2 · 对抗验证**：逐条复核 file:line、写复现、做反驳，剔除误报，定级。
- **阶段 3 · 真实运行验证**：起真实系统跑起来看——跑 playwright real 套件 + API 判别实验 + 不变量审计（`GET /api/ops/graph-consistency`、`checkAxioms`），**通读进程日志**，把每条降级/失败事件归因（曾靠这一步抓到写死锁与 persist 确定性失败）。
- **阶段 4 · 汇总分级输出**（格式见文末）。

### 九个审查维度（每维给"怎么查"，不只是"查什么"）

**A · 架构与分层**
- 分层契约：域层（`src/domain`，同步纯函数）/ 智能层（`apps/api/src/intelligence`，唯一持 LLM）/ 持久层（`packages/db`）/ 路由层 / 前端。查穿透：域层里有没有 I/O、Promise、repo 引用？路由有没有绕过域函数手搓状态？
- 双表示一致性：内嵌软链（relatedThemeIds/contradictsPointIds/evidenceAnchors/supersededByPointId）↔ 图边（belongs_to_theme/contradicts/derived_from/evolves_into）的投影（edge-mapper）→ diff（persist）→ 审计（auditGraphConsistency）链条是否闭合；有没有第三处编码同一事实？
- 全局机制完备性：写串行化（豁免清单是否恰好？释放路径覆盖所有"响应不会完成"的情形吗？）、LLM 预算（**所有** LLM 调用点都过 budget 吗？grep 遍历 complete/chat 调用）、外呼超时（所有 fetch/provider 都有吗？）。
- 每个包装器/工厂/注入点：能力是否透传（spread 或显式转发）？可选能力的 typeof 探测在四档位矩阵下各返回什么？

**B · 业务流程（以用户旅程为单位端到端走查）**
旅程清单：①文本访谈全程（开始→轮次→控制→结束归档）②语音 cascade 全程 ③记忆治理（候选→批准/拒绝→内联修正→整理合并→弃用）④资产操作（确认决策、四类状态流转、标记重要）⑤外部调研（简报、盯梢、auto-run）⑥导入资料→RAG 问答 ⑦播客生成/重合成 ⑧复盘（月/年/雷达）⑨隐私（purge→导出→导入恢复）⑩配置与 playbook。
每步问五件事：前置条件谁保证？失败分支去哪（用户看到什么）？幂等吗（双击/网络重试重放一遍）？并发另一个写进来会怎样？UI 有入口吗（**功能可达性**——存在但无入口 = 死功能）？
- 状态机完备性：对每个枚举字段（session.status、point.status 五态、decision.decisionKind/confirmationStatus/status、debt.status、question.status、memory.status、candidate.status、theme.maturity 六态…）建 **producer/consumer 矩阵**：每个值谁写入、谁消费、有没有"写而无读"或"读了但永不可能出现"的值、非法迁移有没有拦截。

**C · 数据生命周期（核心维度，逐实体建账本）**
对 ProductState 的每个数组 + state_meta 运维尾巴 + 冷层（raw-material）+ 知识索引 + audio 附件，各建一张账本：
- **生产**：谁创建（哪个路由/域函数/LLM/种子）？字段完整性（必填、默认值、枚举合法）？id 生成规则？
- **存储**：surql schema 约束与 types.ts 一致吗？typed 列与 rest blob 有没有影子真相（日期类字段两处存）？
- **消费**：谁读？门控（status/sensitivity/policy）在**每条**消费路径上口径一致吗（域层过滤 vs SQL WHERE vs 前端展示各是一套？）
- **演化**：更新会不会覆盖用户确认（用户确认 > AI 推断的优先级守卫在每条更新路径上都有吗）？
- **删除**：谁删？级联完整吗（A5）？隐私 purge 真的清干净了吗（冷层、索引块、图边、audio、导出残留）？**删除后重引入**（备份导入、purge 后恢复）会产生悬空引用吗——本项目曾因"级联删 turn 后重引入带 anchor 资产"导致 persist 整事务确定性失败。
- 找五类病：孤儿字段（写而无读）、幽灵读（读而永无写）、双写发散、断链（生产口径≠消费口径）、无限增长表（retention 缺失）。
- 建模合理性：冗余字段（已有疑点：decisionKind×confirmationStatus、reviewAt）、平行编码、概念不统一（参考 M1 统一记忆主题的先例——还有同类吗？）。

**D · 一致性与不变量**
- 公理 A1–A5 的覆盖缺口：还有哪些跨实体约束没人管？（例：anchors 的 sessionId 指向的会话必须存在吗？candidate→record 的 sourceCandidateId 闭环？chunkIds 与 rag_chunk 双向一致？）
- **设计公理对撞矩阵**：把全局假设列全（H1 turn append-only、A5 级联删除、降冷剥 turns、diff 基线自愈、revision 服务端权威、边由软链投影、budget 会话重置、写串行化豁免、demo 种子存在……），**两两对撞**找碰撞场景。本项目已实证 H1×A5 碰撞产生 P1 级 bug——同类碰撞大概率不止一处。
- revision 全链：服务端 bump→路由响应→前端采纳（adoptServerState）→去抖 PUT→409 处理，每个环节的 revision 是否权威。

**E · 降级与失败路径账本**
grep 全部 `catch`/`fallback`/`degraded`/`fail.?safe`/`console.warn`，每处记录：{触发条件, 降级行为, 可观测信号(日志/health/UI), 降级后语义是否仍正确, 会否掩盖上游真错}。重点：LLM 失败/超时/预算耗尽、embedding 失败、搜索 provider 链、persist 失败、语音 ASR/TTS 失败、**前端 PUT 的 .catch 静默丢弃**（无后续编辑则永不重试——这类"静默丢用户数据"最优先）。

**F · 安全与隐私**
- 敏感隔离全链路：sensitivity 标记在 存储→访谈上下文→chat 索引→RAG→溯源（recallProvenanceTurns 的 includeSensitive）→导出→**日志**（敏感原话有没有进过 console？）每一环各自验证。
- auth：豁免前缀的实际覆盖面（`/api/health/*` 会豁免其下所有子路径——新端点有没有误放进豁免区？）、生产 token 缺失护栏、WS/媒体 `?token=` 旁路的面。
- 注入：外部不可信文本（导入资料、搜索结果、ASR 转写）进 prompt 前的清洗（sanitizeExternalMaterialText）覆盖**所有**拼接点吗？grep 所有 prompt 组装处逐一对。
- secret：env 的读取/日志/错误响应有没有泄漏面。

**G · 并发与时序**
- 写串行化：MUTATING 清单核对（WS 升级、SSE、流式响应算不算？）、auto-run 豁免的安全论证复核、slot 泄漏面（还有哪些"响应永不完成"的路径？）。
- 前端三方竞态：去抖 PUT × 路由响应采纳 × 轮询刷新；conflicted 时"丢弃本地改动"对每类编辑是否可接受（有没有该 rebase 重放的高价值编辑？）。
- persistQueue × 原生召回读 × 审计的交错语义；flush 的等待语义。
- 幂等清单：把所有 POST 重放一遍（双击面），逐个记录结果。

**H · 观测与运维**
- 静默失败信号覆盖：health 现有 persist.degraded + 图审计端点，还有哪类静默失败无信号（知识索引失败？audio 上传失败？语音会话僵尸？）。
- 日志：关键路径缺日志/噪声日志/敏感内容入日志三查。
- 运维真实可用性：备份导出/导入/迁移脚本真跑一遍（dry-run）。

**I · 前后端契约**
- 每个路由响应 shape × 前端消费点逐一对：`state` 字段是否权威态（本项目曾 27 处路由回传 revision 未 bump 的旧对象 → 前端下一次 PUT 必 409 丢编辑，这是刚修完的模式——查有没有漏网与回归面）；错误码语义前后端一致吗（409 在"已结束/已确认/revision 冲突"三种含义间有没有分支错配）。
- 前端状态覆盖：空态/加载/错误/成功；后端产出但 UI 永不展示的死数据（如 guide 的服务端字段）。

### 方法与工具

- 结构理解用 codegraph（`codegraph_explore`/`codegraph_node`）优先于裸 grep；但 codegraph 曾有"未消费"误报——判死代码前用文本 grep 复核。
- 验证：`npm run typecheck`；`npx vitest run`（全量基线应全绿）；playwright real 套件需先起服务：`set -a && source .env.local && set +a && PORT=3210 npx tsx apps/api/src/server.ts`（后台）+ `npm run dev`（3220），然后 `npx playwright test tests/e2e/real-*.spec.ts tests/e2e/voice-cascade.spec.ts`。
- 不变量：`GET /api/ops/graph-consistency`（dual-surreal 档位）；域层 `checkAxioms`。
- 判别实验：用 node fetch 脚本做最小复现（注意：无 body 的 POST **不要**带 json content-type，fastify 会 400）。
- 阶段 3 结束后**通读**服务进程日志，每条 warn/error 事件都要归因（transient？设计内降级？真 bug？）。

### 有意设计清单（不要当 bug 报）

- 域层同步纯函数 + 内存真值源 + 异步落库（前端 useMemo 同步契约钉死；"全链 async"已被显式否决）
- CWA 公理引擎只报违例、不拦写、不推新事实（D5/D6，刻意不引 OWL reasoner）
- turn 冷层 append-only，persist 永不删 turn；part_of 豁免图审计
- fail-safe 降级遍布是单用户本地工具的可用性取舍——审"可观测性与语义"，不审"存在本身"
- chat 知识索引（八源聚合）独立于 rag_chunk，**刻意**不接原生 rag 召回
- PRODUCT_STORE opt-in、默认 sqlite；当前生产档 dual-surreal
- playwright real-search 有 2 条刻意 skip（慢/联网已单测覆盖）
- 悬空溯源由持久层主动丢弃 + 审计 dangling 单列（H1×A5 根修）
- `createInitialProductState` 含 demo 种子资产（测试要空基底须显式清）

### 重点怀疑区（线索，必须重新验证后才能算发现）

- App.tsx 巨型组件的状态机（采纳/保存/会话生命周期/语音生命周期）分支覆盖与竞态
- 语音 cascade 的错误恢复面（WS 断连、ASR 长静默、echo guard 误吞、僵尸会话清理）
- offload 冷层 × 备份导出/导入的往返完整性（anchors、audio、降冷会话的再水化）
- budget 粒度混用（per-session 桶 vs "system" 桶）与重置时机
- diffIndexableSources 的增量索引覆盖面（哪些实体变更不触发 reindex？）
- theme 的聚合/演化消费面（evolves_into 谁在读？maturity 状态机有没有降级路径？）
- 搜索 provider 链（anysearch/bailian/local-demo）的降级语义与 usage 标注
- audio 附件生命周期（删会话/purge 时清吗？孤儿文件？）

### 输出格式

1. **执行摘要**：九维各一句话结论 + 问题计数（按严重度）。
2. **发现清单**（最严重在前），每条：`{P0-P3, CONFIRMED/PLAUSIBLE, 维度, 标题, file:line, 失败场景, 复现方式, 根因, 修复方案草案, 影响面, 反驳与回应}`。
3. **覆盖证明**：已审且无问题的区域清单（维度×模块矩阵，注明验证方式）——没有这个，"没发现"≠"没问题"。
4. **不建议做清单**：看似问题但修复代价 > 收益，或属有意设计。
5. **方法自评**：哪些区域没到达、置信度低，下一轮建议。
