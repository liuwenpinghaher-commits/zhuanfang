## 二、发现清单（按严重度）

### ★ P0 · persist 确定性失败家族 [RT 全部实测确认]

**根因（一个）**：`normalizeProductState` 允许表达 surreal SCHEMAFULL/ENFORCED 会拒绝的状态，而 persist 对"被拒"没有入库前规整——结果要么整事务确定性失败（基线冻结 wedge，其后所有写永不落权威库，重启全丢），要么 A5 级联在事务内静默删掉 hot state 仍持有的节点（基线照常推进，三份真相发散，重启丢数据）。入口：`PUT /api/state`、`POST /api/state/import`（官方恢复通道）。

- **P0-1 [RT] 节点级静默删除（A5×解耦态）**：PUT 移除 session 保留 note → persist 成功（0 失败）、DB note 被级联删、图审计 missing=1 抓到、基线已推进 → 重启丢 note。`rag_chunk×material` 变体无边投影 → 零信号更隐蔽。（005_p3_cascade.surql:27-36 + storage.ts 不修剪 note.sessionId/chunk.sourceId）
- **P0-2 [RT] 同事务级联删 turn × RELATE ENFORCED——昨日④修复的盲区**：移除 session + 新增 point（anchor→该 session 的 turn）→ `keepOnlyLiveTurnProvenance` 事务前查 turn（还活着）放行 → 事务内 DELETE session 级联删 turn → RELATE 被拒 → 整事务失败、health.degraded、每次重放同败（wedge）。昨日修复只覆盖"turn 过去已删"，漏"同一事务内被删"。判定信息（provenance.sessionId ∈ 本批删除集）现成可用。
- **P0-3 [RT] 非法枚举毒化**：PUT/import 含 `point.status:"已废弃"`（非白名单）→ normalize 放行 → surreal ASSERT 拒 → 同 wedge 形态。枚举唯一强制点在 DB，API 边界零校验；历史上 `draft→active` 迁移（storage.ts:154）证明此类已发生过一次。

**统一修复方向**：persist 前对 next 做"可持久化性规整"——(a) 枚举白名单钳制（非法值规整+警告）；(b) 悬空引用修剪：`note.sessionId`/`chunk.sourceId` 指向本快照不存在的父 → 连同删除或拒绝；(c) `keepOnlyLiveTurnProvenance` 增加"toId 的 sessionId ∈ 本批 session removeIds 则过滤"；(d) 图审计补节点表核对（现仅 5 边表）。

### P1（8 条）

1. **reset 三重失守**（6 来源交叉 + 主控实测冷层） [RT冷层/CODE其余]

2. **前端 autosave 失败零信号 + 重载覆盖**（3 来源） [CODE]
   去抖 PUT 的 catch 空体（App.tsx:267-270），无 notice、无 console、`apiPersistenceEnabled` 从不渲染；持久性失败（401/413/5xx）下每次保存静默失败而 UI 逐次弹"已保存"；刷新 → 采纳服务端旧态并立即覆写 localStorage → 双份俱灭。修复：失败 N 次上浮全局降级横幅。
3. **sqlite 快照损坏静默 demo 化**（E+H） [PLAUS·后果毁灭]
   `state_json` 解析/normalize 抛错 → catch 静默回落 `createInitialProductState()`（含示例数据，连"数据没了"的直观信号都被遮住）→ 任意下一笔写把 demo 基态 UPSERT 回快照行，用户数据永久覆盖。零日志零 health。修复：catch 里 fail-loud + health 字段 + 拒绝启动或只读模式。（sqlite-product-state-repository.ts:46-50）
4. **双写切换/回退无新旧校验**（D6） [CODE]
   回退 sqlite 期间的新数据，在切回 dual-surreal 的第一笔写被旧 surreal 权威静默覆盖（mirror 在比对之前 → digest 恒等零告警）；漏 migrate 直切时处女 surreal 的 demo 种子直接成权威并镜像覆盖 sqlite 真实数据。启动期两库 revision 单调性检查信息齐备但没人用。（server.ts:700-722; dual-write-repository.ts:61-84）
5. **realtime-voice 10 分钟 TTL 从不续期**（B） [CODE]
   长语音访谈（产品核心场景）>10min 后：每次打断 `/interrupt` 静默跳过截断仍回 `interrupted:true` → 逐字稿保留用户没听到的助手长文 → finalize/记忆抽取基于失真转写；cascade TTS WS 断线重连必 404，语音输出到会话结束不可自愈。修复：活跃会话续期 + interrupt 对过期会话如实报错。（realtime-voice.ts:826/133-142/236-318）
6. **POST /api/memory/consolidate 绕过 LLM 预算**（A2） [CODE]
   聚类摘要循环内每 cluster 一次 complete，无 tryConsume、无循环上限、注册时未传 sharedBudget——全库 13 个 complete 调用点唯一漏网，"covers all LLM entry points"声称失实；N 大时还成为超 120s 写锁强放的确定性入口。（memory-candidates.ts:218; server.ts:290）
7. **production 档两处裸 fetch 恒 401**（E+H） [CODE]
   `classifyTurnComplete`/`logCascadeDecision` 用裸 fetch 绕过 authedFetch → 生产 bearer 下语义轮转 Layer-2 永久失效（每轮 fail-safe 成 done:true）、级联决策审计全丢，零信号。（productApi.ts:703/715-719）
8. **28MB 双悬崖**（C2） [CODE·算术]
   ragChunks 1024 维向量存 ProductState 单 blob（~3.5MB/大导入，累计无上限）→ ~8 次大导入撞 28MB PUT 墙 → autosave 永久 413（叠加 P1-2 静默）；导出包只给音频做 18MB 预算，state+冷层不设防 → 备份成功、恢复 413、无分片方案。数据越多备份越要紧，墙越准时。

## 四、不建议做清单

- 全链 async 域层／把推理下沉 DB（fn::/SurrealML）／LIVE query——设计决策依据未变（前端同步契约、CWA、spike 实测阻断）
- turn 表增长治理——H1 是溯源地基，purge 是合法出口，个人量级撑不出问题
- chat 知识索引接 rag_chunk 原生召回——八源聚合是刻意独立设计
- 写锁 120s 强放机制本身——是"极小概率单写覆盖换不冻结"的显式取舍；要修的是让长写不超限（P1-6/P2-20/P2-21），非撤销强放
- localStorage 副本移除——离线降级/首屏缓存价值真实，有 revision 收敛；只需修垃圾键透传（P3-48）
- 幽灵枚举立即清删——先做产品决策（软删 vs 硬删、revert 要不要入口），schema 清理随行
- export 含敏感全文——备份完整性是正确语义（provider secret 已排除）
