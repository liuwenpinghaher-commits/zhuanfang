## 3. 发现清单

### F-01 P1 CONFIRMED · `import` 坏包返回 422，但热态已被覆盖

维度：数据生命周期 / 隐私恢复 / 原子性

证据：

- `apps/api/src/routes/state.ts:197-208`：先构造 `imported` 并执行 `repository.replaceState(imported, { skipReindex: true })`。
- `apps/api/src/routes/state.ts:216-233`：之后才校验 `body.rawMaterials` 的 `sessionId/turns/createdAt`。
- `apps/api/src/routes/state.test.ts:312-335` 现有回归只断言旧冷层没丢，没有断言热态未变。

触发条件：

- 调用 `/api/state/import`。
- payload 带合法 `state` 和非法 `rawMaterials`，例如缺 `turns`。

复现结果：

```json
{
  "statusCode": 422,
  "beforeName": "Mia",
  "afterName": "SHOULD_NOT_APPLY_AFTER_422",
  "hotMutatedDespite422": true
}
```

失败场景：

用户导入一个坏备份包，接口返回 422，用户以为导入失败且现有状态受保护；实际热态已经被新包覆盖。冷层没被清空，但热层已经进入“半导入”状态，之后 autosave/export/业务消费都会基于错误热态继续运行。

根因：

`import` 的 build-then-swap 只覆盖了冷层 raw/audio 条目的校验窗口，没有把热态 replace 纳入同一个原子边界。

修复草案：

- 先完成完整导入计划构建：normalize hot state、校验 rawMaterials、构建 audios、预检查 knowledge rebuild 输入。
- 所有校验通过后再进入提交阶段。
- 提交顺序要让错误不会产生“422 但热态已变”：至少把 `repository.replaceState` 移到 raw/audio 校验之后；更稳的是统一 `buildImportTransaction()`，最后一次性提交热态和冷层。
- 补测试：`/api/state/import` 对非法 rawMaterials 返回 422 后，断言热态字段、revision、冷层都未变。

反驳与回应：

- 反驳：导入本来是全量覆盖，热态覆盖是用户确认后的意图。
- 回应：覆盖可以是意图，但 422 是拒绝语义。拒绝响应后状态已经改变，是假失败/部分提交，不是设计选择。

### F-02 P1 CONFIRMED · runtime config 刷新后能力页 ready，但业务路由仍使用启动时 provider 快照

维度：架构与分层 / 前后端契约 / 降级可观测性

证据：

- `apps/api/src/server.ts:119-120`：`refreshProviderClients()` 会刷新同一个 `providerClients` 对象。
- `apps/api/src/routes/system.ts:364-381`：PATCH `/api/system/config` 写入 env 后调用 `options.refreshProviderClients?.()`。
- `apps/api/src/server.ts:199-224`：system 路由传的是 getter，所以 capabilities 能看到刷新后的 provider。
- `apps/api/src/server.ts:237-341`：多数业务路由注册时传 `...providerClients` 或具体字段，捕获的是注册时值，不是 live getter。
- `apps/api/src/routes/search.ts:64-75`：搜索路由运行时只读 `options.anySearchClient` / `options.bailianSearchClient`，没有重新解析 provider registry。
- `apps/api/src/e2e/real-llm-journeys.real.test.ts:239-241`：real AnySearch 旅程要求至少一个非 `example.local` 的真实 URL，当前失败。

判别实验：

用 `env = {}` 启动 server，PATCH 设置 `ANYSEARCH_ALLOW_ANONYMOUS=true` 与 `ANYSEARCH_BASE_URL=http://127.0.0.1:9`，然后请求 capabilities 和 `/api/search/briefs`。

```json
{
  "patchStatus": 200,
  "capabilityStatus": "ready",
  "capabilityActive": false,
  "briefStatus": 200,
  "taskStatus": "degraded",
  "degradedReason": "AnySearch API key 未配置，已使用本地壳生成需复核简报。",
  "firstSourceUrl": "https://example.local/anysearch/runtime%20provider%20refresh%20audit/1"
}
```

fresh 测试同向失败：

```text
npx vitest run apps/api/src/e2e/real-llm-journeys.real.test.ts
1 failed | 5 passed | 1 skipped
AssertionError: expected 0 to be greater than 0
apps/api/src/e2e/real-llm-journeys.real.test.ts:241
```

全量测试同向失败：

```text
npx vitest run
Test Files  1 failed | 123 passed (124)
Tests       1 failed | 1224 passed | 1 skipped (1226)
```

失败场景：

用户在系统配置页填入/启用 provider，能力页显示 `ready`，但搜索、播客、访谈、RAG、chat、memory 等业务路由仍拿着启动时的 undefined client，继续本地降级。用户看到的是“已配置但不生效”，并且降级返回 200，容易被误判为功能正常。

根因：

`providerClients` 被设计为可刷新对象，但路由注入模式混用：system 用 getter，业务路由大多用 spread 快照。刷新只改变对象属性，不会改变已传入 options 对象里的 undefined 字段。

修复草案：

- 建立统一的 `ProviderRegistry`，暴露 getter：`getAnySearchClient()`、`getBailianChatClient()`、`getEmbeddingClient()` 等。
- 业务路由运行时通过 getter 取当前 client，而不是注册时 spread。
- 先修 search，再按同一模式覆盖 podcast/interview/import/corpus/review/rag/chat/memory/realtime。
- 补测试：PATCH runtime config 后，同一 server 实例的业务路由必须使用刷新后的 client；capabilities 与 route 行为必须一致。

反驳与回应：

- 反驳：部分 provider 变更可能本来需要重启。
- 回应：当前 system config PATCH 明确调用 refresh，capabilities 也展示 ready；产品语义已经承诺运行时生效。若需要重启，capabilities 和配置 UI 必须标记 restartRequired，而不是 ready。

### F-03 P2 CONFIRMED · realtime voice 使用 `process.env`，与注入 `runtimeEnv` / capabilities 分叉

维度：语音链路 / 配置一致性 / 生产可达性

证据：

- `apps/api/src/routes/realtime-voice.ts:47-61`：route options 有 `env`。
- `apps/api/src/server.ts:263-270`：注册 realtime voice 时传了 `env: runtimeEnv`。
- `apps/api/src/routes/realtime-voice.ts:538`：TTS WS upgrade 读取 `process.env.DASHSCOPE_API_KEY ?? process.env.BAILIAN_API_KEY`。
- `apps/api/src/routes/realtime-voice.ts:641`：ASR WS upgrade 读取 `process.env.DASHSCOPE_API_KEY ?? process.env.BAILIAN_API_KEY`。
- `apps/api/src/routes/realtime-voice.ts:714-726`：`buildRealtimeVoiceConfig()` 读取 `process.env`。
- `apps/api/src/routes/realtime-voice.ts:803-832`：session 创建调用 `buildRealtimeVoiceConfig()`，默认 voice 读取 `process.env.BAILIAN_REALTIME_VOICE`。
- `apps/api/src/routes/system.ts:493-511`：capabilities 基于 `options.env ?? process.env` 判定 realtime ready。

判别实验：

临时清空相关 `process.env`，用注入 env 启动 server：`{ DASHSCOPE_API_KEY: "dummy-key", BAILIAN_REALTIME_TRANSPORT: "websocket" }`。

```json
{
  "capabilityStatus": "ready",
  "capabilityActive": true,
  "configApiKeyConfigured": false,
  "configConfigured": false,
  "sessionStatus": "not-configured"
}
```

失败场景：

测试、嵌入式部署或 runtime config 页面通过 `buildApiServer({ env })` 注入了 key，能力页显示 realtime ready；但 `/api/realtime-voice/config` 和 `/api/realtime-voice/sessions` 仍认为未配置，WS ASR/TTS upgrade 也会因读不到 `process.env` 而关闭。

根因：

realtime voice 路由只把 `options.env` 用于 WS Origin/auth 检查，没有把它传入 config/session/WS provider resolver。

修复草案：

- 改造 `buildRealtimeVoiceConfig(env)`。
- `createRealtimeVoiceSession(payload, realtimeClient, stateRepo, env)` 使用同一个 env。
- ASR/TTS WS upgrade 优先用 `options.env` 和 live provider getter，不直接读 `process.env`。
- 补测试：注入 env 但清空 process.env 时，capabilities、config、session、WS provider resolver 结果一致。

反驳与回应：

- 反驳：生产进程通常就是 `process.env`，所以线上可能不受影响。
- 回应：项目已有 runtime config PATCH 和 scoped env real tests，说明注入 env 是受支持路径；同一 server 内两个接口给出相反状态是契约问题。

### F-04 P2 CONFIRMED · `purge(all)` 冷层清理失败返回 500，但热态已经清空

维度：隐私 / 数据生命周期 / 原子性

证据：

- `apps/api/src/routes/state.ts:309-326`：构造 full purge 热态。
- `apps/api/src/routes/state.ts:326`：先 `repository.replaceState(purged, { skipReindex: true })`。
- `apps/api/src/routes/state.ts:329-336`：之后才 `rawMaterialRepository?.deleteAll()`、`audioRepository?.deleteAll()`、`knowledgeIndexRepository?.deleteAll()`。

判别实验：

注入一个 `deleteAll()` 抛错的 raw material repo。

```json
{
  "statusCode": 500,
  "beforeCounts": {
    "sessions": 0,
    "points": 1,
    "notes": 1
  },
  "afterCounts": {
    "sessions": 0,
    "points": 0,
    "notes": 0
  },
  "hotPurgedDespite500": true
}
```

失败场景：

用户执行彻底清空，接口返回 500，用户以为清空失败；实际热态已被清空，但冷层可能残留。结果同时具备数据丢失风险和隐私残留风险，后续 export/import/召回语义都可能错。

根因：

多存储清理没有事务、补偿或明确的部分成功响应；热态提交发生在冷层清理之前，后续异常直接走全局 500。

修复草案：

- 把 purge 设计成显式两阶段：预检查/提交计划/执行/汇总。
- 若冷层无法清理，应在热态改变前失败，或返回结构化 `partialFailure` 并记录审计事件，不能 500 且静默留下已改变热态。
- 如果必须跨库提交，至少保存 pre-purge 快照并在失败时做补偿，或把响应改成 207/200 degraded，明确列出哪些 store 已清、哪些失败。
- 补测试：raw/audio/knowledge 任一 deleteAll 抛错时，断言热态是否符合设计语义；当前最小目标是“不允许 500 后热态已清而响应假失败”。

反驳与回应：

- 反驳：purge 是破坏性操作，尽可能清掉热态也许更符合隐私优先。
- 回应：隐私优先不能返回 500 假失败，也不能让冷层残留无结构化信号。若设计选择是“尽力清”，响应和 audit 必须如实表达部分成功。

### F-05 P2 CONFIRMED · `/api/state/reset` 是全量清空数据，但服务端无确认令牌

维度：安全治理 / 隐私 / 操作防误触

证据：

- `apps/api/src/routes/state.ts:66-84`：POST `/api/state/reset` 不读取 request body，不校验 confirm。
- `src/App.tsx:1481-1484`：只有前端 `window.confirm`。
- `src/api/productApi.ts:619-620`：API 客户端 `resetState()` 发送无 body POST。
- `apps/api/src/server.ts:637-645`：Origin 守卫只拦浏览器跨站 mutating request；无 Origin 的 curl/服务端互调/脚本仍可直接 reset。
- 对照：`apps/api/src/routes/state.ts:181-188` import 要 `REPLACE_ALL_STATE` / `PURGE_PERSONAL_DATA`；`state.ts:286-293` purge 要 `PURGE_PERSONAL_DATA`。

判别实验：

```json
{
  "statusCode": 200,
  "beforeCounts": {
    "points": 1,
    "notes": 1
  },
  "afterCounts": {
    "points": 0,
    "notes": 0
  },
  "resetAcceptedWithoutConfirm": true
}
```

失败场景：

任何本地脚本、测试工具、服务端互调、错误 curl 都可以无 body 清空全部数据。虽然生产 auth 和 Origin 守卫降低了外部攻击面，但 reset 的破坏性与 import/purge 一样，服务端治理却更弱。

根因：

reset 历史上被当作“回到示例/空状态”快捷操作；现在代码与 UI 文案已经承认它会删除真实访谈、资产、记忆、逐字稿，但服务端契约没有同步升级。

修复草案：

- 要求 `{ confirm: "RESET_ALL_DATA" }` 或复用 `{ confirm: "PURGE_PERSONAL_DATA" }`，并更新 `productApi.resetState()`。
- 前端继续保留 `window.confirm`，但它只作为 UX 防误触；服务端确认令牌作为 API 防误调用。
- 更新所有测试中无 body reset 调用。
- 若保留测试便利，可新增测试 helper，不让生产路由保持弱契约。

反驳与回应：

- 反驳：本地单用户工具，生产还有 auth 与 Origin 守卫。
- 回应：这不是认证绕过类 P0/P1，而是破坏性 API 的一致性和防误调用问题。import/purge 已经实现服务端 confirm，reset 不应成为同类操作的例外。

## 6. 建议修复顺序

1. 先修 F-01 import 原子性：这是错误响应后热态已变，最容易造成用户误判和备份恢复污染。
2. 修 F-02 provider live registry：它已经导致 real AnySearch 测试失败，且影响多条业务路由。
3. 修 F-03 realtime env resolver：与 F-02 属同一配置一致性家族，可共享 provider/env getter 设计。
4. 修 F-04 purge 部分提交语义：决定采用“失败前不改热态”还是“尽力清理但结构化 partial response”，再补测试。
5. 修 F-05 reset confirm：影响面广但实现机械，需要批量更新测试调用。

## 7. 不建议作为本轮 bug 处理

- Vite `vendor-livekit` chunk warning：当前 build 通过，这是性能/包体优化项，不是本轮 P1/P2 功能故障。
- fail-safe/local-demo fallback 的存在：降级是有意设计；本轮问题在于 ready 与真实路由不一致、以及降级掩盖 provider refresh 失效。
