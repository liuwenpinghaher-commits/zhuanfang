1. `dual-surreal` 已能识别“Surreal 近空、SQLite 有真实数据”，但只告警仍继续启动；首笔写会确定性覆盖 SQLite 冷备。

## 3. 正式发现

### F-01 · P1 · CONFIRMED · dual-surreal 权威库可疑时只告警，首笔写仍会覆盖 SQLite 冷备

维度：持久化 / 运维恢复 / 数据一致性

证据：

- `apps/api/src/server.ts:790-813`：检测到 `surrealRev <= 1 && sqliteRev > 1` 时记录 `dual_surreal_authority_suspect`，但随后仍创建 `authoritative: surreal, shadow: sqlite`。
- `apps/api/src/dual-write-repository.ts:75-105,130-135`：权威写成功后，shadow 直接 `replaceState(next)`，再做比对；旧 SQLite 内容先被覆盖，比对只能看到覆盖后的相等状态。
- 本轮内存判别实验：shadow 的 1 条真实 point 在近空 authoritative 首笔写后变为 0，`realDataOverwritten=true`。
- 定向 Playwright 启动时真实观察到该告警：Surreal revision 0、SQLite revision 56；进程仍继续进入 `dual-surreal`。

触发条件：回退 SQLite 后直接切回 `dual-surreal`、漏跑迁移、或测试环境误继承 `PRODUCT_STORE=dual-surreal`。

失败场景：服务成功启动；首个 mutating 请求以近空 Surreal 快照为基线，把 SQLite 冷备中的真实数据镜像覆盖。告警不能阻止数据丢失，也不能让 API 调用者知道本次写不安全。

修复草案：

- 生产/持久模式下检测到 authority suspect 必须 fail-closed，拒绝监听端口。
- 提供显式 override，例如 `ALLOW_DUAL_SURREAL_AUTHORITY_MISMATCH=true`，只能由人工恢复流程使用。
- 切换前比较 digest/实体数而不只比较 revision；迁移脚本成功后写入 cutover marker。
- 首次启动 dual-surreal 时禁止 shadow mirror，直到两库等价检查通过。

反驳与回应：dual-surreal 是 opt-in，操作员应先迁移。回应：代码已经能识别“未迁移且首写会覆盖”，此时继续启动不是合理的 opt-in 责任边界；fail-closed 成本远小于冷备被覆盖。

### F-02 · P1 · CONFIRMED · Playwright 的“memory”隔离并非内存，且会继承本机 PRODUCT_STORE

维度：测试隔离 / 运维 / 数据安全

证据：

- `playwright.config.ts:14-35`：API webServer 设置 `PRODUCT_STATE_DB_PATH: "memory"`，但没有设置 `PRODUCT_STORE`。
- `apps/api/src/env.ts:6-20`：`startServer()` 启动时会加载 `.env.local` 中未被测试 env 覆盖的键。
- `apps/api/src/server.ts:743-817`：`startServer()` 不使用 `createDefaultProductStateRepository()` 的 sentinel 逻辑，而是直接把 `productStateDbPath` 交给 SQLite/dual 工厂。
- `packages/db/src/sqlite-product-state-repository.ts:31-35`：`new DatabaseSync(options.dbPath)` 将字符串 `memory` 当普通文件路径。
- 临时目录实验：`PRODUCT_STORE=sqlite + PRODUCT_STATE_DB_PATH=memory` 启动并关闭后，`sqliteFileCreated=true`。
- 定向 Playwright 实跑继承到 `dual-surreal`，新建了仓库根目录 `surreal/`；本轮已将该测试产物移动到 `/tmp/zhuanfang-audit-20260710/`，没有删除或修改原有 `memory` 文件。

触发条件：运行 `npm run test:e2e`，且 `.env.local` 设置了非 sqlite 的 `PRODUCT_STORE`；即使没设置，`memory` 仍是磁盘文件而非内存库。

失败场景：E2E 跨轮次共享旧数据；测试可能连接非预期存储档位；当 reset 调用补齐 confirm 后，测试可把近空 Surreal 权威状态镜像覆盖本地 `memory` SQLite 文件。

修复草案：

- `startServer()` 识别 `memory/:memory:/in-memory`，直接注入 `createInMemoryProductStateRepository()` 及内存冷层。
- Playwright 显式设置 `PRODUCT_STORE=sqlite` 或专用 `memory` 档，并设置隔离 cwd/临时绝对路径。
- 测试启动时断言 `/api/system/capabilities` 的实际 store 与期望一致；不一致立即停止。
- `startServer` 的 store 选择提取为纯函数，覆盖所有档位与 sentinel 组合。

反驳与回应：`memory` 文件已被 `.gitignore` 忽略，不会提交。回应：问题不是 Git，而是测试状态污染和误连接；忽略文件不能提供运行隔离。

### F-03 · P1 · CONFIRMED · reset 冷层失败仍返回 200，前端 API 失败也会本地清空并宣称成功

维度：隐私 / 失败语义 / 前后端契约

证据：

- `apps/api/src/routes/state.ts:73-90`：先 `repository.resetState()`，随后逐库 `deleteAll()`；冷层异常只 `console.warn`，最终仍返回 `next`。
- `src/App.tsx:1481-1511`：`productApiClient.resetState()` 任意异常都会切离线、本地 `resetProductState()`，最后统一显示“全部数据已清空”。
- 故障注入：raw delete 抛错时响应仍为 200，热态 point 从 1 变 0，冷层 raw material 仍存在。

触发条件：raw/audio/knowledge 任一 SQLite I/O 故障、后端不可达、API 返回 4xx/5xx。

失败场景：用户得到“全部数据已清空”，但逐字稿、录音、索引或服务端热态仍可能存在；刷新后旧数据还可能重新出现。

修复草案：

- reset 返回结构化清理回执；任一 store 失败不得返回无条件 200 success。
- 前端网络失败只能显示“仅本地视图已重置，服务端未确认删除”，不得复用成功文案。
- reset 与 purge 合并为同一治理 primitive，UI 的“清空示例”若只需删除 demo 数据应使用专用 scope/seed 标记，而不是全量删除。
- 增加 raw/audio/knowledge 三种失败注入与 UI 错误态测试。

反驳与回应：reset 的尽力清理能最大化隐私删除。回应：尽力清理可以保留，但必须把 `partialFailure` 返回给用户；200 假成功会阻止用户继续补救。

### F-04 · P1 · CONFIRMED · import/purge 的 build-then-swap 只覆盖校验，不覆盖存储执行失败

维度：恢复 / 删除 / 跨库原子性

证据：

- `apps/api/src/routes/state.ts:258-270`：import 先 `replaceState(imported)`，再依次 raw `deleteAll/put`、audio `deleteAll/put`。
- `state.ts:316-345`：`purge(all)` 先删 local-object、raw、audio、knowledge，最后才提交热态；后序 store 失败时前序删除无法恢复。
- `state.ts:348-373`：`purge(interviews)` 先提交热态，再清 raw/audio/knowledge；冷层失败时返回 500，但热态已改变。
- legacy/raw ProductState import 没有 `rawMaterials/audios` 字段时，旧冷层原样保留，接口仍以“替换全部状态”返回 200。
- 故障注入结果：
  - import raw delete 失败：500，profile 已变为导入值，旧冷层仍在；
  - purge all 的第二个 store 失败：500，热态未变，但 raw 已删除；
  - legacy hot-only import：200，旧 raw material 仍存在。

触发条件：任一底层存储执行失败，或导入旧格式/裸 ProductState。

失败场景：恢复和清空都可能进入“响应失败但一部分已变”或“响应成功但旧隐私数据仍在”的状态；后续 export、RAG、召回会把不同时代的数据重新混合。

修复草案：

- 建立治理事务 journal：记录 pre-state digest、每个 store 的计划/完成状态、补偿动作和恢复入口。
- SQLite 热态/raw/audio/knowledge 尽量合并到同一 SQLite connection/transaction；跨 Surreal/local-object 时用 staged namespace + 原子指针切换。
- import 对缺失冷层字段必须要求显式模式：`preserve-cold` 或 `replace-all`；默认不能静默保留。
- 音频条目非法不得静默跳过；返回完整校验错误和未恢复清单。

反驳与回应：跨数据库无法获得真正 ACID。回应：无法全局 ACID 不等于只能裸顺序执行；journal、staging、补偿和结构化 partial result 都能消除假成功并支持恢复。

### F-05 · P1 · CODE-CONFIRMED · 离线本地分叉没有重连/合并，服务恢复后可覆盖离线工作

维度：前端状态一致性 / 用户旅程 / 数据丢失

证据：

- `src/App.tsx:343-360`：首次 mount 只调用一次 `getState()`；失败后仅 `setApiPersistenceEnabled(false)`，没有重连任务。
- `App.tsx:240-294`：autosave 失败后没有 retry timer；只有下一次 `productState` 内容变化才会再试。首次失败只记 console，第二次才显示 notice，但 notice 声称“恢复后会自动重试”。
- `App.tsx:715-743`：离线开始专访明确提示“稍后可同步”，但没有 outbox/sync API。
- 多个后续 API 成功路径调用 `adoptServerState()` 整体采纳服务端状态；它不会合并此前离线修改。
- reload 时初始化先读 localStorage，随后远端 `getState()` 成功会整体 `setProductState(remoteState)`，本地未同步版本被覆盖。

触发条件：启动或 autosave 时后端短暂不可达；用户继续访谈/编辑；后端恢复后刷新页面或执行一个成功的服务端操作。

失败场景：离线修改只存在 localStorage，用户看不到可靠的“未同步”账本；恢复连接后旧服务端状态覆盖本地修改。UI 的“稍后可同步/自动重试”与实现不一致。

修复草案：

- 引入持久 outbox，记录 base revision、operation id、patch/command 和状态。
- 后端恢复时先拉取 server revision，再执行三方合并或逐操作重放；冲突必须展示给用户，不得整体覆盖。
- autosave 使用有界指数退避并显示明确 pending count；页面离开前提示未同步。
- 若短期不实现同步，移除“稍后可同步”承诺，并把离线模式标为独立本地工作区，禁止自动采纳远端覆盖。

反驳与回应：localStorage 只是缓存，服务器才是权威。回应：系统同时允许用户在离线模式继续生产真实数据并承诺稍后同步；一旦允许写，localStorage 就不再只是可丢缓存。

### F-06 · P1 · CODE-CONFIRMED · 备份可不完整或不可导入，但 API 类型和 UI 均显示成功

维度：备份恢复 / 隐私治理 / UI 真实性

证据：

- `apps/api/src/routes/state.ts:111-169`：音频导出预算固定 18MB，超额项只进入 `audioOmittedSessions`；包体超过 64MB 只在 `importCompatibility.exceedsImportLimit` 标记。
- `src/domain/backup.ts:28-45` 的 `BackupRestoreRehearsalReport` 不包含 raw materials、audios、`audioOmittedSessions`、`importCompatibility`。
- `src/api/productApi.ts:477-479` 将响应强制断言为上述窄类型。
- `src/features/profile/ProfileView.tsx:81-119,341-352` 下载后无条件显示“已下载 JSON 备份包”，导入 200 后无条件显示“已从备份恢复”，不检查遗漏/超限。
- `state.ts:238-255` 对非法音频条目静默 `continue`，import 不返回 skipped 清单。

触发条件：录音 base64 总量超过 18MB、热态/raw material 使包体超过 64MB、或导入包中有不完整音频条目。

失败场景：用户看到备份成功，随后执行 purge；恢复时部分录音缺失或整个包 413，才发现备份不能完整恢复。

修复草案：

- 定义真实 `StateExportBundle` 类型，包含 completeness、omitted artifacts、bytes、import limit、digest。
- UI 在下载前显示“完整/不完整/不可直接导入”，不完整时禁止用“备份成功”作为唯一状态。
- 大音频使用独立归档或流式 zip；JSON 只保存 manifest + content digest。
- import 返回 restored/skipped/missing 清单，并要求用户确认部分恢复。

反驳与回应：遗漏信息已写进 JSON，技术上不算静默。回应：正常用户只看到 UI 成功态，类型系统也把字段抹掉；把警告藏在下载文件里不构成产品可见信号。

### F-07 · P1 · CONFIRMED · 真实 Provider 测试与脚本会把签名 URL/密钥前缀写入日志

维度：安全 / 隐私 / 供应商凭据

证据：

- `apps/api/src/e2e/real-llm-journeys.real.test.ts:348,358` 输出完整 TTS `audioUrl` 和 URL 前缀；本轮实跑确认 URL 含签名查询参数。报告不记录具体值。
- `scripts/verify-tts.mjs:43,94,135` 输出 key 前缀和完整音频 URL。
- `scripts/spike-tts-prosody.mjs:27`、`spike-tts-instruct.mjs:32`、`spike-tts-pcm.mjs:51`、`spike-asr-create-response.mjs:68`、`verify-providers.mjs:120` 输出 provider key 前缀。

触发条件：本地或 CI 运行真实 provider 验证脚本/测试。

失败场景：CI 日志、终端录屏或协作记录保存临时可访问音频链接、签名参数或凭据前缀；生成内容可能来自私人笔记/访谈。

修复草案：

- 建立统一 `redactUrl()`：只保留 origin + pathname hash，移除全部 query/fragment。
- 禁止输出任何 key 前缀；只输出 `configured: true/false`。
- 给日志增加敏感字段 lint/test，扫描 `token/key/secret/signature/url` 的直接输出。
- 对已经进入共享日志的签名 URL 按供应商能力吊销或等待过期，并收紧日志保留。

反驳与回应：前缀不是完整 secret，签名 URL 会过期。回应：签名 URL 在有效期内就是 bearer capability；前缀与其他泄漏组合会增加凭据识别风险，且没有验证价值。

### F-08 · P2 · CONFIRMED · reset confirm 契约未同步到浏览器 E2E，真实旅程从 422 开始

### F-09 · P2 · CONFIRMED · real-provider 测试存在 false-green 与 jsdom 噪声

- real-provider 测试使用 node environment；AnySearch 配置存在时外部失败应失败，或以框架原生 skip 明确计入 skipped。
- 拆分“路由接线测试”和“外部 provider smoke”：前者 mock 网络且必须稳定通过，后者允许环境门控但不能 return 伪装通过。
