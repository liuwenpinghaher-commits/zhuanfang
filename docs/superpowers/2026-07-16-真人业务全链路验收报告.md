## 1. 验收目标

本轮不是只验证“页面能打开、接口返回 200、测试是绿色”，而是按真实业务逻辑验证：

1. 用户以真实身份、真实主题、真实麦克风进入系统。
2. AI 能进行有上下文、有推进、有追问价值的真实专访。
3. 专访结束后，系统能产出准确、有价值、可编辑、可追溯的知识资产。
4. 记忆候选经过真实治理后，能在后续专访中被正确召回。
5. 数据在正常退出、重启、导出、空库恢复后仍然可靠。
6. 系统最终确实帮助用户形成长期知识积累，而不是只生成一次性摘要。

## 2. 验收原则

- 当前代码、当前运行服务、当前数据库与真实供应商响应是最高证据。
- 历史报告只作为回归线索，不作为当前事实。
- 自动化用户、预设脚本、API 直调只能证明相应技术链路，不能替代真人专访质量结论。
- 任何“未执行”“跳过”“外部服务不可达”均不得计为通过。
- 运行期间不修改业务代码；发现问题只记录证据，等待用户决定是否进入修复阶段。

## 6. 已确认缺陷

### P0：完整备份恢复后，知识来源追溯丢失，但审计仍显示 `ok: true`

#### 现象

源库完整导出后，导入另一套空数据库：

- 核心热态数据一致。
- 冷层 raw material 数量一致，内容逐字一致。
- 导入接口返回 200。
- 导出完整性仍显示 `complete`。
- 恢复库图审计顶层仍显示 `ok: true`。

但真实来源召回结果发生变化：

| 数据库 | 对同一 point 调用 `recallProvenanceTurns` |
|---|---|
| 源库 | 返回对应用户原话 1 条 |
| 恢复库 | 返回空数组 |

源库审计：

```text
expectedCount=11
actualCount=11
danglingProvenanceCount=0
ok=true
```

恢复库审计：

```text
expectedCount=11
actualCount=6
danglingProvenanceCount=5
ok=true
```

恢复过程中服务端同时输出：

```text
surreal_dangling_provenance_dropped count=5
```

被丢弃的 5 条来源关系涉及：

- 1 个 point
- 2 个 memory candidate
- 1 个 note
- 1 个 theme

#### 根因链

1. 已完成会话会把逐字稿从热态剥离到 cold raw material，热态中的 `session.turns` 为空。
2. 导出包同时包含这个无 turns 的热态 state 与完整 raw materials。
3. 导入事务会恢复热态、raw materials 和 audio，但不会把 raw material 中的 turns 重新投影为图数据库的 `turn` 节点。
4. 热态资产仍携带 evidence anchors；持久层准备建立 `derived_from` 时发现目标 turn 节点不存在，于是主动丢弃这些边。
5. 图审计把这些缺失归入 `danglingProvenanceCount` 后，从 `missingInDb` 中移除；顶层 `ok` 的计算没有包含 `danglingProvenanceCount`，于是出现假绿色。

#### 用户影响

这不是纯内部计数问题。后续专访预取上下文时，会沿 `derived_from` 获取观点与决策的原始证据。恢复后这些来源为空，将导致：

- 知识资产无法反向查看或引用原话。
- 后续专访只能看到结论，缺少形成结论的上下文。
- AI 更难区分用户原话、系统归纳和推断。
- 跨会话积累的可信度下降。
- “完整备份可恢复”的承诺与实际行为不一致。

#### 相关代码位置

- `packages/db/src/surreal/surreal-product-state-repository.ts:607`：真实来源召回依赖 `derived_from -> turn`。
- `packages/db/src/surreal/surreal-product-state-repository.ts:897`：图审计实现。
- `packages/db/src/surreal/surreal-product-state-repository.ts:913`：悬空来源从 missing 中被移出。
- `packages/db/src/surreal/surreal-product-state-repository.ts:942`：`ok` 未纳入 `danglingProvenanceCount`。
- `packages/db/src/surreal/surreal-product-state-repository.ts:1063`：turn 仅从热态 `session.turns` 投影。
- `packages/db/src/surreal/surreal-product-state-repository.ts:1085`：不存在的来源端点被过滤。
- `apps/api/src/routes/state.ts:507`：导入事务恢复热态与 cold raw/audio，但没有 cold raw turn 图重建。
- `apps/api/src/recall/prefetch-recall.ts:55`：后续专访上下文会消费来源召回结果。

### P1：个人档案显示“已保存”早于服务端真正持久化

真人主题准备阶段通过真实 UI 修改“当前关注”并点击“保存档案”。页面立即显示“已保存”，但在提示出现后马上关闭浏览器，再查服务端仍是旧值；随后新建会话也使用了旧主题。

当前代码行为：

- `ProfileView.handleSaveProfile` 调用本地 `setProductState` 后立即设置 `profileSaved=true`。
- 服务端保存由 App 的 autosave effect 延迟 300ms 执行。
- 页面在延迟窗口内关闭时，用户已经看到了“已保存”，但 PUT 尚未发生。

第二次操作改为明确等待 `PUT /api/state` 成功响应后再继续，服务端才保存了正确主题。

用户影响：

- “已保存”是本地采纳信号，不是持久化成功信号。
- 用户快速离开或关闭页面时可能丢失刚编辑的档案。
- 后续专访可能在用户不知情时使用旧关注主题。

### P2：专访上下文采用了正确主题，但启动页标题与开场问题仍然泛化

正确保存“当前关注”后，通过真实 UI 创建了组织/关系会话：

```text
mode=organization
topicHint=企业如何进行 AI Native 转型：个人提效显著，但组织效率提升有限，瓶颈在哪里，如何让组织真正提效？
```

但启动后的可见界面仍显示：

```text
标题：组织/关系专访：今天想聊点什么？
开场：今天先从一个最近反复出现的问题讲起：它具体发生在哪个场景里？
历史引用：你最近有一个反复出现的问题。
```

这说明后台主题传递成立，但卡片标题、开场与用户可见准备信息没有体现具体主题。用户无法从界面确认 AI 是否真的理解了本场目标，也会降低“已做专访准备”的可信感。真人作答后需继续观察实际追问是否围绕正确 `topicHint`，以区分仅 UI 泛化还是访谈引擎同样泛化。

### P1：阶段总结严重错抓主题，且把局部时间片段冒充主线

在第 15 个用户回答后点击真实 UI 的“阶段总结”，系统反馈：

```text
我先做阶段总结：你反复回到的其实是“在2025年11月的投资”背后那层更在意的东西。
下一步最值得问的是：它能不能被一个小一点的具体例子先验证一下？
```

但“2025 年 11 月”只来自一个被否决的销售全流程 AI 投资案例。前 15 轮真正反复出现的主线是：个人任务提速没有压缩端到端价值流，瓶颈在决策权、在制品、跨部门激励、共同上下文和风险反馈。

代理受访者在下一轮明确纠正后，主持人能够承认并回到主线，说明纠错链路可用；但阶段总结本身未达到“帮助用户看见思路演化”的设计目的，且可能让真实用户误以为系统形成了错误长期理解。

### P1：记忆候选会重新写回用户已经纠正过的观点

本次生成的 10 条待审记忆中，有一条写成：

```text
组织效率受制于工作在制品、决策权、跨部门激励、数据可用性和风险反馈；
这五项构成AI Native转型的结构性前提，缺一不可。
```

但受访者在第 13 轮已经明确纠正：“结构条件不是转型开始前必须全部满足的准入门槛，而应当在试点中一起改变；否则最需要转型的组织永远无法开始。”

候选前半句能概括瓶颈，后半句“结构性前提，缺一不可”却与用户的显式修正冲突。双轨笔记的“我学到了什么”正确保留了这次修正，而记忆抽取又把旧观点写回长期候选，说明不同产物之间缺少矛盾一致性检查。该候选应在 UI 治理中被拒绝，不能进入长期记忆。

### P2：跳过控制能换题，但主题抽取会截断成无意义片段

第 19 轮追问开始重复此前的部门阻力问题。点击“跳过这个问题”后，系统确实换成了低压力问题，控制行为生效；但反馈写成：

### P2：所有追问都显示同一条泛化“历史引用”，没有形成真实可核验引用

25 轮主持人追问及 3 次控制反馈均显示：

```text
引用历史：你最近有一个反复出现的问题。
```

服务端 `strategyTrace` 也把同一句保存为 `referencedMemory`。它既没有引用当前会话中的具体原话，也没有引用已确认长期记忆；在空记忆库中反复展示，会造成“系统好像记得什么”的错觉。实际追问大多能跟随当前回答，但可见引用和可追溯记忆价值没有成立。

### P2：长访谈后半程追问呈现稳定的“复述 + 泛化阻力问题”模式

前半程主持人能围绕委员会等待、风险控制、评测成本、激励和权力边界逐步深入；使用“换个角度”后也成功从评测工程转向组织激励。后半程多次出现：

1. 先用“所以你认为……”复述上一轮；
2. 再追问“有没有阻力或困难”；
3. 以“比如……”给出宽泛例子。

这种模式保持了话题连续性，但在 20 轮以后重复感明显，较少主动做跨轮矛盾检查、量化验证或回到尚未解决的关键问题。代理受访者需要主动把对话推进到管理角色、能力建设和 90 天路径，主持人的“真正专访感”仍不足。

### P1：第二场后台实际引用了确认记忆，但页面展示的是另一条主题摘要

第二场跨会话专访的服务端 `strategyTrace` 在 5 轮中都记录了同一条真实确认记忆：

```text
个人工具普及率不是组织提效的充分条件；组织产出取决于端到端流动效率，
而流动效率由共同上下文、决策等待、在制品数量和反馈速度共同决定。
```

但页面每轮显示的“引用历史”始终是：

```text
AI Native不是部署更多模型，而是让组织围绕客户结果重构决策权、资源、数据和反馈回路。
```

后者来自主题/笔记摘要，不是本轮策略轨迹中的 `referencedMemory`。因此后台跨会话记忆使用成立，但前端引用透明度失真：用户看到的不是模型本轮实际使用的长期记忆，无法核查模型是否正确套用旧知识。

### P1：资产对话引用编号与来源类型不一致

重启后通过真实 UI 向资产对话询问已确认长期判断。系统成功召回确认记忆、观点、逐字稿和笔记，但正文引用出现三类错误：

1. 正文写“`[5]（note）`”，实际 citations 数组中 note 是 `[4]`，`[5]` 是另一段客户续费案例逐字稿。
2. 结尾引用客户 ID 案例时写 `[6]`，但响应总共只有 5 个 citations，不存在 `[6]`。
3. 回复称“来源依据全部为你亲述的原始记录”，但 memory、point、note 都是系统加工后的派生资产，只有 transcript 才是原始记录。

召回内容本身基本正确，且 transcript 可反向定位到具体 turn；但编号、类型和来源权威层级混乱，会让用户无法判断一句结论到底来自已确认记忆、系统观点、会后笔记还是原始逐字稿。

### P2：长期主题“一键开始”自动切到决策专访，用户没有看到模式选择依据

今日访谈台显示“关于 AI Native组织的本质的专访”，点击“一键开始”后实际创建：

```text
mode=decision
title=决策专访：关于「AI Native组织的本质」的专访
```

开场问题直接选择第一场未解决的 AI 代理审计责任问题。这条路由在内容上合理，也成功利用历史资产，但 UI 没有在点击前说明为何从“长期主题”转为“决策专访”，用户可能误以为仍在进行长期主题回访。

### P1：实时语音 WebSocket 忽略 API 配置并硬编码 `3210`

验收 Web 通过 `VITE_PRODUCT_API_BASE_URL=http://127.0.0.1:3310` 正常访问独立 API，但点击“开始录音”并授权麦克风后立即提示：

```text
语音连接已断开
语音识别中断,请重新点击录音继续。文字输入不受影响。
```

逐层核对结果：

- `GET /api/realtime-voice/config` 返回 `configured=true / apiKeyConfigured=true / transport=websocket`。
- 直接连接 `ws://127.0.0.1:3310/api/realtime-voice/ws/:sessionId`，依次收到 `proxy.connected`、`session.created`、`session.updated`，12 秒内连接稳定。
- `src/App.tsx` 的 `realtimeApiWsBaseUrl()` 在 HTTP 页面下固定返回 `ws://<hostname>:3210`，没有读取 HTTP API 已使用的 `VITE_PRODUCT_API_BASE_URL`。
- 验收时 `3210` 无监听进程，因此浏览器连接在麦克风授权后立即失败；临时把 `3210` TCP 转发到 `3310` 后，同一页面无需改代码即可成功建立语音会话。

这不是供应商或麦克风不可用，而是前端语音基址与产品 API 基址分叉。默认端口启动时会被掩盖，任何非默认开发端口、隔离验收环境或多实例部署都会复现。

### P1：无真实用户输入期间仍生成伪用户回合并继续追问

第一段合成受访者语音被正确识别并触发追问后，页面一边继续开着麦克风，一边通过扬声器播放主持人回复。测试代理没有再播放第二段受访者回答，但系统随后自动写入：

```text
用户表达：的一个黄总。
主持人：不太明白你提到的“一个黄总”和之前说的内容有什么关系，可以详细解释一下吗？
```

这条伪用户回合进入了服务端权威 session，并触发了新的 LLM 调用。当前证据能证明“无测试受访者输入时产生了伪回合”，但不能进一步区分来源是主持人 TTS 回灌、现场环境声，还是 ASR/VAD 误触发；因此不把具体根因写成已确认事实。无论来源是哪一种，产品目前都缺少阻止低可信转写直接进入权威逐字稿与 LLM 的有效门槛。对真实专访而言，这会污染策略轨迹、主持人判断和最终知识资产，属于高优先级语音完整性缺陷。

### P1：真实语音转写末尾截断，实时字幕还混入现场背景语音

合成原文末尾为：

```text
以及由谁在什么条件下批准、暂停和回滚。
```

最终写入权威 session 的用户回合末尾变成：

```text
以及由谁在什么条件下。暂停和回。
```

实时字幕一度还在后面追加了与测试原文无关的现场语音片段。服务端最终持久化没有保留全部追加内容，但关键句本身仍被截断。该现象会改变责任治理语义，不能只按“ASR 有文字”判定质量通过。

### P2：“本次不保存”数据边界成立，但结束成功提示与真实结果相反

在语音会话中点击“本次不保存”后，页面正确显示“不写入长期资产”；停止录音并点击“结束并生成档案”后，权威状态核对为：

- 该语音 session 已从热态删除；
- `GET /api/sessions/:id/raw-material` 返回 404；
- note、point、question、decision、debt、theme、memory candidate、confirmed memory 数量均未增加；
- 图一致性仍为 `expected=42 / actual=42 / dangling=0`。

因此不保存的数据边界实际成立。但页面同时显示：

```text
专访档案已生成
双轨笔记和认知资产已更新。
```

这条成功提示与真实行为完全相反，会让用户误以为隐私边界失效或资产已经写入。

### P2：中途“不保存”会话缺少明确恢复入口，容易再创建一场重复会话

准备语音验收时，先创建了一场组织模式会话并切换“不保存”。离开页面后，“实时专访”入口显示的是重新开始路径；再次点击开始后创建了新的决策模式会话，而原组织会话仍以 active 状态留在服务端。当前首页虽能显示一条“未完成的专访”，但多场 active 会话下没有清楚说明选择规则，也没有在实时专访入口直接提供当前会话恢复。最终留下了一场只有控制反馈的 active 会话和一场更早的零轮次 active 会话。

## 6.3 真实 Chrome 麦克风代理验收

### 执行方式

- Chrome 打开真实验收页面 `127.0.0.1:3320`。
- 麦克风权限选择“仅这次访问时允许”，实际设备为 Mac 内置麦克风。
- 受访者内容由 macOS `say` 使用中文语音从真实扬声器播放，不通过 API、输入框或浏览器脚本注入转写。
- 页面使用真实 ASR、真实专访 HTTP 追问和真实 TTS；服务端权威状态用于核对最终回合。
- 测试回答开头明确说“这是合成受访者语音，仅用于验收”，避免把代理内容误当成用户本人经历。

### 真实链路结果

在修正验收端口连通条件后，页面显示：

```text
实时语音会话已就绪
级联模式 (ASR→分析→TTS) 已连接
```

合成语音内容围绕“AI 代理责任可追溯性”，要求重放依据包含规则版本、输入快照、证据来源、权限、模型和工具版本、阈值、置信度、调用链、异常与人工干预。系统形成的第一轮权威记录为：

```text
user: 这是合成受访者语音，仅用于验收……以及由谁在什么条件下。暂停和回。
assistant: 你提到的这些字段，在实际的日志重放中，哪一个最容易被遗漏或者记录不准确？
referencedMemory: 日志不能只证明“发生过”，还要能重放为什么做出这个判断。
strategy: mechanism_probe
```

这证明以下技术环节不是模拟通过：

1. Chrome 权限与真实麦克风采集；
2. 浏览器 WebSocket 与服务端语音代理；
3. 扬声器语音经空气进入麦克风后的真实 ASR；
4. ASR 最终文本进入专访策略与 LLM；

## 9. 当前判定

当前不能判定系统达到最终设计目的，原因有三类：

1. **已确认产品缺陷**：完整恢复会丢失知识来源图，且健康审计假绿色。
2. **内容与语音质量缺陷**：阶段总结错抓主题；跳过线索截断；历史引用始终泛化；长访谈后半程追问重复；至少一条记忆候选违背用户已明确纠正的观点；真实语音还出现末尾截断和无测试受访者输入时的伪回合。
3. **验收证据缺口**：代理闭环已经覆盖两场专访、记忆治理、重启、跨会话召回和真实 Chrome 麦克风技术链路，但尚未发生用户本人真实经历、本人声音的长时专访和主观质量评价。

| 1. 真实身份、真实主题、真实麦克风 | 主题与 Chrome 麦克风链路已执行；受访内容仍是代理虚构案例和合成语音 | **未完成** |
