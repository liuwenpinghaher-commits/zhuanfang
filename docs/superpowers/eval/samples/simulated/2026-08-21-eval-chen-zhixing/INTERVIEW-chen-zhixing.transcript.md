我叫陈知行，最早是做物理的，博士做无序系统和统计物理，2023 年才半道转进 AI。这两年主要在做基座模型的预训练，跟数据配比、scaling 这些事打交道，万卡集群上跑过不少实验。最近我反复在想一件事：我们这个行业其实已经不太担心模型能不能做到某件事了，真正难的是想清楚要做什么——就是这件事是不是被良好定义。这个转变对我冲击挺大的，因为它意味着稀缺的不再是算法,而是判断力。

## 2. 主持人

你说难的是把问题良好定义。最近一次在万卡集群上跑实验，让你觉得“这个问题根本没被良好定义”的具体是哪一次？当时卡在哪了？

## 3. 陈知行

去年11月，我们在万卡集群上跑一个号称“提升数理逻辑”的scaling实验。当时上面的诉求很直接：下个月发版，数学benchmark分数要超竞品5个点。数据团队就疯狂往语料里塞合成数学题，把开源竞赛题翻来覆去地洗。

跑了三周，烧了上千万的算力。loss曲线看着特别漂亮，极其平滑。但一上评测，发现模型只是在“背题”——把GSM8K的句式稍微改个条件，它直接崩盘。

那天深夜我盯着监控大屏，觉得挺荒谬的。大家以为卡在算力或数据量，其实是“提升数理逻辑”这个问题根本没被定义清楚。预训练本质是压缩，你喂大量同质化合成数据，它确实压缩了这些题的分布，但这只是窄分布过拟合，不是推理。强化学习是在压缩之上做窄分布雕刻，底座连真实逻辑分布都没压缩好，RL怎么雕？

我们不是在解决技术问题，是在用万卡算力掩盖业务目标的模糊。卡和数据的分配其实是一种政治，上面要能发PR的分数，下面就只能用数据迎合。你觉得，现在还有几家敢停下来，去重新定义一下到底什么是真正的“推理能力”？

## 4. 主持人

你说上面要PR分数，下面迎合。那在这个迎合里，你当时具体拍板了哪个数据配比的决定？

## 5. 陈知行

当时我拍板把合成数学和代码数据的配比从常规的 2% 直接拉到了 15%。为了凑够这 13% 的增量，我硬生生砍掉了 8% 的通用书籍和高质量网页语料。

做决定的那天下午，数据负责人跟我吵了一架。他说这破坏了通用语言的长尾分布，模型会退化成只会解方程的“做题家”。从统计物理的角度看，这就好比强行改变了系统的哈密顿量，把原本均匀的相态逼到了奇点。我当然知道他说得对，预训练本质是压缩，你喂大量同质化合成数据，它确实压缩了这些题的分布，但这只是窄分布过拟合，强化学习再怎么雕刻也救不回来。

但我还是签字了。为什么？因为如果不这么干，下个月发版数学分数就超不过竞品，整个团队大半年的 scaling 实验在老板眼里就是零。卡和数据的分配其实是一种政治，组织如何做 top-down 的赌注比单点技术更决定成败。

现在回头看，那 15% 的数学数据除了换来发布会上 PPT 里高出的那几个 benchmark 点数，对产品形态毫无帮助。模型能力在头部三家已经被拉平，纸面 benchmark 大多是噪声，真正的差距在产品形态和数据飞轮。你觉得，如果现在重新让我选，我敢不敢顶着发版压力，把数学配比压回 2%，去赌一个真正通用的底座？

## 6. 主持人

我不替你回答敢不敢。你刚才说真正的差距在“数据飞轮”，那现在你们跑通的飞轮，具体是靠用户的什么行为在喂数据？

## 7. 陈知行

其实现在所谓的“飞轮”，早就不靠用户点那个“赞”或“踩”了，那种数据噪声太大，根本没法用。我们现在真正在挖的，是用户在 Agent 交互里的“放弃”和“手动接管”行为。

前两个月我们在调一个处理长代码库的 Agent。一开始数据团队以为用户多轮对话的完整上下文就是好数据，后来我拉了后台日志一看，根本不是。真正有价值的数据飞轮，是用户让 Agent 找个 bug，Agent 输出了五步推理，用户在第四步的时候，突然手动把代码改对了，然后直接结束了对话。或者更常见的，Agent 在那死循环，用户等不及直接关掉网页。

我们让工程团队把这几万条“中途放弃”和“手动接管”的轨迹全捞了出来，洗成 DPO 的偏好对。这就成了我们做后训练最宝贵的负反馈数据。预训练本质是压缩，这些真实的交互轨迹就是最真实的分布，比用大模型自己合成的那些完美 trajectory 强一万倍。强化学习是在压缩之上做窄分布雕刻，拿这种带着人类真实挫败感和纠错逻辑的数据去雕，Agent 能力才真的能涨。

所以你看，飞轮不是靠用户夸你好，而是靠用户在你的产品里“受挫”并自己动手。你觉得，现在有几家公司的产品形态，能自然地收集到这种“用户接管”的轨迹？

## 8. 主持人

你说把“第四步手动改对”洗成 DPO 偏好对。那在这个偏好对里，被算作 chosen 的，到底是用户接管后写对的那行代码，还是 Agent 原本的前四步加上用户的修改？

## 9. 陈知行

都不是。这个问题当时我和后训练组的老林在白板前抠了半个晚上。

如果只把用户接管后写对的那行代码算作 chosen，脱离了前四步的 context，模型根本学不到为什么要这么改，这就退化成了单步的代码补全，根本不是 Agent 规划。但如果把“Agent前四步加上用户修改”整个序列全算作 chosen，坑更大：Agent 的前四步恰恰是“被用户放弃”的轨迹，里面大概率藏着导致用户不耐烦的微小瑕疵，比如多绕了个弯或者格式不够干净。直接当正样本喂进去，模型就会把这些冗余动作学过去。

最后我们拍板的方案是：rejected 是 Agent 完整的错误轨迹；chosen 是 Agent 的前四步，但在用户接管的那个 state（状态）节点，我们强行把 action（动作）替换成了用户写的那行代码，并直接截断。本质上，我们是在做条件概率的雕刻，教模型“在走到这个特定的 state 时，你应该输出用户的那个 action”。

这其实就是我常说的，问题有没有被良好定义。DPO 看着是个简单的偏好优化，但你怎么定义 state 和 action 的截断边界，直接决定了模型是在学全局规划，还是在学打补丁。你觉得，如果连 state 的边界都定义模糊，跑再多万卡又有什么用？

## 10. 主持人

既然截断边界这么关键，你们怎么验证这个“强行替换”的方案就是对的？跑对比实验时，它比全量 rejected 具体多涨了多少个点？

## 11. 陈知行

验证这个方案，我们没看那些纸面 benchmark，那大多是噪声。我们直接拉了内部 500 个真实的开源长代码 issue 做盲测。

跑对比实验时，基线组是把包含用户修改的完整序列当 chosen。结果挺戏剧性的，强行替换的方案在 issue 修复成功率上比基线高了 4.5 个点，从 32% 涨到了 36.5%。

但当时我和老林都没高兴太久。因为人工抽检时我们发现，模型变得特别“啰嗦”。它会在执行修改前，加一堆“让我先检查一下上下文”的废话。这说明我们在做窄分布雕刻时，把用户接管时的“急躁”特征也学进去了。用户当时可能心里骂着娘敲下那行代码，模型却把这种短促的 action 和前面冗长的 context 强行绑死了。

所以，到底哪个方案是“对”的？其实没有绝对的对。纸面指标涨了 4.5 个点，但产品的交互体验变差了。这就回到了我常说的，对 AGI 时间线保持克制，更担心问题是否被良好定义。如果问题定义只是“提高修复率”，那方案是对的；如果定义是“做一个好用的代码 Agent”，那这就是个失败实验。你觉得，为了这 4.5 个点的内部指标，牺牲掉对话的流畅度，这算不算一种技术上的自嗨？

## 12. 主持人

既然没有绝对的对，那你们最终发版时，是带着这4.5个点的提升直接上线，还是回滚了？

## 13. 陈知行

最后既没直接上，也没回滚。发版前三天的评审会上，产品VP死盯着那4.5个点的修复率要上，但一线产品经理拿了几十段模型啰嗦的回复拍桌子，说这会让用户觉得我们在教他写代码，体验极差。

当时会议室挺僵的。我最后提了个折中方案：保留这个底座，但在SFT（监督微调）阶段，临时插入了一个“简洁度”的偏好数据。说白了，就是用另一批高质量的、不带废话的Agent交互轨迹，去中和掉模型学来的“急躁”。这其实是个挺 dirty 的工程 trick，从物理角度看，就是给系统强行加个正则项。

最后发版的模型，修复率涨了大概3个点，没到4.5，但对话长度缩减了40%。

你看，这就是现实。没有完美的算法，只有基于当前组织资源和产品目标的妥协。个人英雄主义的时代过去了，真正稀缺的不是你能在实验室里跑出多漂亮的曲线，而是你能不能在这种多方拉扯中，定义出一个大家都能接受的、足够好的版本。你觉得，如果当时我们死磕那个完美的RL目标，这个版本还能赶上年底的发布吗？

## 14. 主持人

我不回答你“能不能赶上”。你刚才说“真正稀缺的是定义出大家都能接受的版本”。但在发版前三天那个僵持的会议室里，当你提出加“简洁度”去中和时，产品VP和一线产品经理，是真的达成了共识，还是因为你有技术决定权，他们不得不接受？

## 15. 陈知行

其实都不是。那天会议室里，产品VP听完我的方案，沉默了大概十秒，然后问了句：“上线后如果用户反馈变笨了，谁背锅？”一线PM则直接翻了个白眼，嘟囔了一句：“这方案太糙了，根本不符合我们的交互SOP。”

我确实有技术决定权，但在现在的头部实验室，这种权力不是用来强压别人的，而是用来“兜底”的。我当场拍了板：“如果上线后客诉率因为啰嗦上升超过0.5%，或者修复率没保住3个点，算我的绩效事故。”

他们最终接受，不是因为怕我，而是因为算了一笔账：如果推翻重来，重新定义RL的奖励模型去解决根本问题，万卡集群上至少要多跑两周，烧掉大几千万算力，发版直接开天窗。在现有的资源约束下，我的“创可贴”方案是唯一的非零解。

这就是为什么说卡和数据的分配是一种政治。技术决定权在很多时候，其实是承担业务风险的筹码。大家达成的不是“这个方案最完美”的共识，而是“在有限时间内，这是唯一能交差且风险可控”的共识。你觉得，在现在的AI实验室里，还有多少技术决策，本质上是算力预算逼出来的妥协？

## 16. 主持人

你当时承诺客诉率上升超过0.5%就算你的绩效事故。实际上线后，这个数字到底是多少？你背锅了吗？

## 17. 陈知行

实际上线后的第一周，我每天早上到工位第一件事，就是让数据同学把客服后台的工单报表拉出来。客诉率最终只涨了 0.12%，远低于 0.5% 的生死线。从考核指标上看，我没背锅，绩效保住了。

但我其实还是“背锅”了，只是换了个方式。客诉虽然没爆，但那个 Agent 的次日留存率悄悄掉了 3 个百分点。用户没去骂客服，他们只是默默地不再打开了。产品 VP 拿着留存曲线找我，绝口不提客诉，只问了一句：“模型确实不啰嗦了，但为什么感觉它变笨了？”

这就是典型的分布偏移。我加的那个“简洁度”正则项，不仅压住了废话，还把模型在长上下文里进行复杂推理的“思考链”给压没了。在物理里这叫过阻尼，系统为了快速达到稳态，牺牲了探索能力。模型为了显得干脆，直接跳步了。

所以我没背客诉的锅，但背了留存的锅。这也印证了我一直说的，真正的差距在产品形态和数据飞轮。你定义了一个“简洁”的目标，模型就真给你演化出一个“偷懒”的局部最优解。你觉得，在强化学习这种窄分布雕刻里，我们是不是永远无法完全预测模型会找到哪个奇怪的解？

## 18. 主持人

留存掉了3%。产品VP拿着曲线找你的时候，你是用“过阻尼”向他解释，还是直接在下个版本把那个“简洁度”的补丁撤了？

## 19. 陈知行

我肯定不会跟他扯“过阻尼”，在商业语境里用物理黑话解释业务下跌，是最懦弱的推脱。我也没敢直接撤补丁，因为一旦撤了，之前压下去的客诉率马上反弹，修复率的指标也得跟着掉。

那个周末我睡在实验室的行军床上，盯着Loss曲线熬了两个通宵。我让数据团队换了个思路：既然强加的“简洁度”SFT数据把模型的思考链给压没了，那我们就去捞那些“用户没有中途接管，且Agent一次性给出完美长推理”的真实交互轨迹。我们把这批高质量轨迹洗出来，专门做了一版恢复思考链的SFT。

本质上，产品VP要的是“既不啰嗦，又不笨”，这在数学上是个多目标优化问题。靠打补丁、加正则项是解不开的，必须回到数据飞轮里，用更高质量的数据去支撑。

这其实就是我一直强调的，问题有没有被良好定义。如果只盯着“简洁”这一个指标，模型就会给你演化出“偷懒”的局部最优解；只有把“高质量推理”和“简洁表达”同时在数据定义里锚定，模型才能学到真正的平衡。你觉得，在现在的AI实验室里，有多少看似完美的产品需求，最后都变成了数据团队在垃圾堆里找黄金的苦力活？

## 20. 主持人

你刚才强调“问题有没有被良好定义”。那你用来筛选这批“完美长推理”轨迹的具体判断标准是什么？是自动化脚本跑出来的，还是人工筛的？

## 21. 陈知行

一开始我带的博后小赵写了个自动化脚本，逻辑很简单：过滤掉中途报错的、执行步骤超过50步的、最后没跑通的。跑出来大概十万条数据。但我抽检了五十条就发现不对劲，这十万条里全是简单的增删改查，模型闭着眼睛都能写对，根本谈不上“长推理”。

这就是典型的“问题没定义好”。脚本只能过滤“错误”，但定义不了“高质量”。

后来我和小赵在白板前重新定义了“完美”。我们把标准从“一次做对”改成了“带有效自我纠错的做对”。具体来说，我们在脚本里加了一个特征：轨迹里必须包含至少一次从 `error` 到 `fix` 的闭环，而且 fix 之后代码必须跑通。

这才是真正的长推理。模型不是一开始就全知全能，而是能看懂报错，能反思自己哪行代码写错了。我们用这个新标准重新去捞数据，十万条里只筛出了不到两千条。然后这两千条，全部丢给外包做人工校验，确保它的思考过程不是在那儿瞎循环。

其实你看，所谓的数据飞轮，不是盲目堆量。你定义问题的颗粒度，决定了数据的纯度。如果当时我们直接把脚本跑出来的那十万条喂进去，模型只会学到一种“遇到简单题就一次过，遇到难题就死循环”的坏习惯。你觉得，在现在这种卷数据的环境里，有多少团队还在用这种“只看结果对错”的粗糙标准在浪费算力？

## 22. 主持人

所以你其实是用“定义error到fix的闭环”，把算力的浪费转嫁成了外包的人工苦力活，对吗？但这2000条数据喂进去后，之前掉的那3%次日留存，涨回来了吗？

## 23. 陈知行

“转嫁”这词不太准确，但确实是把算力压力变成了人力成本。那两周，我们组三个博后每天跟外包逐条对齐什么叫“有效纠错”。其实这就是我一直说的，真正稀缺的是把模糊的事定义清楚的人。外包不是苦力，是帮我们标定数据分布边界的标尺。

至于那3%的留存，没完全涨回来，只回升了大概1.2%。

那天我盯着大盘数据看了很久。我们熬通宵洗出的2000条数据，在万卡集群上跑了三天，留存只捞回一半。后来产品VP拉着我复盘，他指着漏斗图说，留存没涨，是因为用户在等待模型输出那几十秒的长推理时，等不及直接关掉了。

我们在实验室死磕数据配比、做窄分布雕刻，把推理能力提上去了，但在产品形态上，没给用户“它正在深度思考”的预期。头部三家的模型能力其实早被拉平了，纸面benchmark大多是噪声，真正的差距在产品形态和数据飞轮的咬合度上。

这也让我更确信，对AGI时间线保持克制。我们总担心模型能不能做到，但其实更该担心问题有没有被良好定义。当模型真的做到时，产品接得住吗？你觉得，如果当时我们在前端加个“深度思考中”的动画，那剩下的1.8%留存能回来吗？

## 24. 主持人

你们后来加上这个动画了吗？加了之后，那剩下的1.8%留存涨回来了吗？

## 25. 陈知行

加了。但不是那种骗人的假进度条。当时前端排期满了，负责人死活不肯加纯UI动画。我在茶水间堵他，达成的交易是：我们后端在流式输出时，先把模型的内部思考链以灰字形式吐出来，前端只加个打字机效果。这不算大改UI，但能让用户看到“它确实在想”。

结果呢？那1.8%的留存不仅涨回来了，还多涨了0.5%。用户看到灰字在动，耐心明显变好了。

但代价是什么？算力成本。因为用户知道模型会“深度思考”，他们开始发更复杂的长文本，甚至故意给模型下套。平均每次请求的输入Token数暴涨了30%，单次推理的GPU时间直接超标，那个季度的推理预算提前半个月就烧光了。

这就很有意思了。我们在算法端千辛万苦洗数据、做RL雕刻，把模型变聪明了；在产品端加了个灰字交互，把用户耐心拉长了；最后用户用更复杂的Prompt，把我们的推理算力又吃光了。这就是真实的数据飞轮，它不是完美的闭环，是个螺旋上升的成本黑洞。你觉得，这种算法、产品、用户三方博弈转出来的飞轮，最后到底是在给谁打工？
