# SurrealDB 整体替换存储层 — 可行性/成本/风险评估

- 日期：2026-06-21
- 性质：架构评估（非实现 spec）。结论先行，供决策。

## 0. 结论（TL;DR）

**不建议**用 SurrealDB 整体替换当前存储层——**当前阶段（单用户、本地、数据小）**。

迁移的真实成本不在"换数据库"，而在**重写整个应用的数据范式**：148 个域层纯函数、551 处对整 `ProductState` 的引用、56 个端点、前后端全量同步、95 个测试文件，全部建立在"加载整状态→纯函数变换→整存"之上。SurrealDB 是按记录 CRUD/查询的不同范式，等于推倒重来。而它的卖点（原生向量/图）在当前 61 条向量、未来 1-2 千块的规模上，JS 余弦微秒级即可解决——用不上。

**值得重估的触发条件**：多用户、向量到十万~百万级、或要把"图+向量+全文"当一等公民做复杂联合查询。届时单独立项评估。

---

## 1. SurrealDB 是什么（力求准确）

多模型数据库（Rust）：文档 + 图（`RELATE`）+ 关系表 + **原生向量检索**（HNSW / MTREE 索引，余弦/欧氏 KNN）+ **原生全文检索**（BM25 分析器）。查询语言 SurrealQL（类 SQL 但不同）。

部署形态：
- **服务进程**：`surreal start`（单二进制），Node SDK 经 WS/HTTP 连接。
- **Node 嵌入式**：`@surrealdb/node` 提供进程内引擎（`mem://` / `surrealkv://` / `rocksdb://`），**可不起独立服务**——这点我先前说"必须起服务"是不准确的，更正。但嵌入式是**原生 addon**（各平台预编译二进制、数十 MB），且相对年轻。

成熟度：1.0 GA 2023-09，2.x 2024；向量检索是较新功能。对比 SQLite（数十年战检验、本仓用的是 **Node 内置 `node:sqlite`，零安装**）。

---

## 2. 被替换的现状（量化）

- 存储：`node:sqlite`（`DatabaseSync`，Node 25 内置，零外部依赖）。单 `state.sqlite` 存整个 `ProductState` JSON blob（乐观锁 revision、全量 PUT 同步），+ 冷层 `raw-material.sqlite` / `audio.sqlite`。
- 域层：**36 个文件、148 个导出纯函数**，签名几乎都是 `(state: ProductState, ...) => ProductState`；全仓 **551 处** `ProductState`/`cloneState` 引用。
- API：**56 个端点**，多数是"读整状态→纯函数→整存"。
- 数据模型：`ProductState` **29 字段、25 个数组**（sessions/notes/points/memoryRecords/...）。
- 前端：持有整个 `productState`，autosave 全量 PUT + revision 乐观锁（22 处同步逻辑）。
- 测试：**95 个测试文件**全部基于整状态纯函数模型。
- 现状"复杂度"：单 blob 膨胀问题**已被冷热拆分解决**（原始稿/音频移出热 blob，blob 现 1.79MB）。

→ 现状不是"数据库太弱"，而是"应用是围绕整状态内存对象 + 纯函数设计的"。这套**能跑、已测、零依赖**。

---

## 3. 迁移真实涉及什么（成本的大头）

把 SurrealDB 当**普通文档库**用（只换持久化，不动范式）几乎没意义——还是整存整取，白受运维成本。要拿到 SurrealDB 的价值（按记录查询/向量/图），必须把范式从"整状态纯函数"改成"按记录 CRUD + 查询"：

1. **域层重写**：148 个纯函数从 `state => state` 改为对 DB 记录的读改写（事务、并发、查询）。这是工作量主体。
2. **乐观锁/同步重设计**：现在靠整状态 revision；改 DB 后要按记录/集合做并发控制 + 前端不再持整状态、改为按需查询/订阅。前端 22 处同步 + 大量"读 productState.xxx"的组件要改。
3. **56 端点重写**：从"整状态"改为按集合查询/写入。
4. **数据建模**：25 个数组 → 25 个表/集合 + 关系（memoryEdges → 图边、relatedThemeIds → 关系）。SurrealQL 重写所有检索（记忆召回、主题聚合、时间线、RAG）。
5. **测试重写**：95 个测试文件大半失效/需重写（它们断言纯函数行为）。
6. **运维/依赖**：引入 `@surrealdb/node` 原生 addon（平台二进制、构建链），或起 `surreal` 服务；备份从"拷 sqlite 文件"变成 DB 导出。
7. **数据迁移脚本**：把现有 state.sqlite/冷层导进 SurrealDB。

> 粗估：**数周到数月**的重写 + 回归，期间功能停滞、风险贯穿全栈。chat/素材库被无限推迟。

---

## 4. 真实收益（诚实）

- **原生向量检索**：替代 JS 余弦 + 拟建的 knowledge_chunks 手工索引。**但**当前 61 向量、未来 1-2 千块，JS 余弦微秒级——收益接近 0。HNSW 在十万+才有意义。
- **原生图**：memoryEdges/主题图成一等公民，复杂图查询更顺。**但**现有图查询简单（标签/邻接），JS 已够。
- **消除单 blob/全量 PUT 的 28MB 墙**：按记录存天然没有此墙。**但**冷热拆分已实际解决该墙。
- **统一存储**：一个 DB 替代几个 sqlite 文件。**但**几个嵌入式 sqlite 文件并不构成实际痛点。

→ 收益多为"理论上更优雅"，在当前规模缺乏可量化回报。

---

## 5. 成本/风险

- **巨量重写**（域/API/前端/测试）+ 功能冻结，是最大成本。
- **丢弃已验证底座**：把 95 测试绿、跑通的记忆/主题/资产/冷层/音频全推平重来。
- **新依赖与成熟度风险**：原生 addon 跨平台构建、SurrealDB 相对年轻、向量功能新，对单用户本地工具是不必要的不确定性。
- **学习/维护**：SurrealQL + 新并发模型的长期维护成本。

---

## 6. 什么时候值得（决策标准）

满足**任一**才重估：
- 走向**多用户/多设备**，需要服务端并发与按记录权限。
- 向量规模到**十万~百万级**（大量长文档/语料），JS 余弦扛不住。
- 要把**图+向量+全文**做成核心查询能力（复杂联合检索）。
- 整状态内存模型出现**真实**性能/内存瓶颈（目前没有）。

均不满足 → 维持现状。

---

## 7. 更轻的替代（如果痒点是"原生向量"）

- **不换架构拿原生向量**：`sqlite-vec` 扩展给现有 SQLite 加向量检索（注：`node:sqlite` 的可加载扩展支持需先验证；不行则 `better-sqlite3` + sqlite-vec）。比上 SurrealDB 小得多。
- **图**：memoryEdges 已建模邻接，无需图数据库。
- **本功能（chat/素材库）**：knowledge_chunks 一个 SQLite 表 + 复用现有嵌入 + JS 余弦，**完全够用**，与已验证架构一致，低风险快交付。

---

## 8. 建议

1. **现在**：维持 `node:sqlite` + 整状态范式；按原计划做 chat + 素材库（knowledge_chunks 增量小表）。
2. **未来**：若出现 §6 任一触发条件，再单独立项评估存储现代化——届时优先评估**渐进路径**（sqlite-vec 加向量、或按集合拆 sqlite），SurrealDB 仅在多用户/大规模/图优先时才进入候选。
3. **不建议**把存储层替换塞进当前功能迭代。
