## S1 · 嵌入式 live query / changefeed 支持性

**方法**:mem:// 与 surrealkv:// 各跑一遍。① SDK managed `.live("t")` 订阅后 CREATE/UPDATE 看通知;`LIVE SELECT * FROM t;` 经 `.query()` 看返回;拿 uuid 走 `.liveOf(uuid)` 再订阅。② `DEFINE TABLE cf CHANGEFEED 1d` + 写入 + `SHOW CHANGES FOR TABLE cf SINCE ...`。脚本:`s1-live-changefeed.mjs` / `s1b` / `s1c` / `s1d` / `s1e`。

**原始关键输出**:

- managed `.live("t")`(表预先存在与否都一样):
  ```
  managed sub.id = undefined
  managed .live() 收到 0 条(表预先存在)
  ```
- unmanaged 路(`LIVE SELECT` → uuid → `liveOf`):
  ```
  uuid = f9385825-094d-4495-a7ca-191f700fb510 Uuid$1
  [liveOf msg] {"queryId":"f9385825-…","action":"CREATE","recordId":"t:x","value":{"id":"t:x","v":1}}
  [liveOf msg] {"queryId":"f9385825-…","action":"UPDATE","recordId":"t:x","value":{"id":"t:x","v":2}}
  liveOf 收到 2 条
  ```
- `LIVE SELECT * FROM 不存在的表` 直接抛 `NotFoundError: The table 't2' does not exist`(须先建表)。
- CHANGEFEED(`SHOW CHANGES FOR TABLE cf SINCE 0 LIMIT 10;` 与 `SINCE d"2020-01-01T00:00:00Z"` 均可):
  ```
  [{"changes":[{"define_table":{…"name":"cf"…}}],"versionstamp":"116895018756014080n"},
   {"changes":[{"update":{"id":"cf:a","v":1}}],"versionstamp":"116895018756145152n"},
   {"changes":[{"update":{"id":"cf:a","v":10}}],"versionstamp":"116895018756145154n"},
   {"changes":[{"delete":{"id":"cf:b"}}],"versionstamp":"116895018756210688n"}]
  ```

**结论**:
- **live = 可用,但只有 unmanaged 路**:`query("LIVE SELECT * FROM t;")` 拿 `Uuid` → `db.liveOf(uuid)` → `.subscribe(handler)`,CREATE/UPDATE(含完整 value)真实送达。SDK 的 managed `db.live(table)` 在嵌入引擎下**坏的**(`sub.id === undefined`、0 通知、不报错——静默失效),不要用。
- **changefeed = 完全可用**:`SINCE 0` 与 `SINCE d"…"` 都工作,versionstamp 单调递增。
- 三个工程坑:
  1. **versionstamp 是 BigInt** → `JSON.stringify` 直接抛 `TypeError: Do not know how to serialize a BigInt`,消费侧必须自带 replacer/转 string。
  2. **定义任何 CHANGEFEED 表后,每次写入 stderr 打十几行 `dbg!` 调试噪声**(`surrealdb-core-3.0.2/src/kvs/timestamp.rs:272` 遗留的 dbg! 宏;实测无 changefeed 表时零噪声,仅 stderr 不进 stdout)。服务端日志会被灌;上线前需评估 stderr 过滤或接受。
  3. live 订阅对不存在的表直接报错,须在 DEFINE TABLE 之后建。

**对 R 系列**:R5 可以走推送(liveOf 路)+ changefeed 游标轮询双保险,与方案"不依赖 live"一致;R1 流水表加 `CHANGEFEED 7d` 功能上成立,但要吃下 stderr dbg 噪声(建议 R1 落地时实测服务进程日志量,必要时推迟 CHANGEFEED 到 R5)。

## S2 · 大 bytes 值性能(音频入库守门)

**方法**:surrealkv:// 新库,SCHEMAFULL 表 `DEFINE FIELD data ON audio TYPE bytes`(3.0.2 直接接受该写法),SDK 侧传 Node Buffer/Uint8Array。1/5/20MB 随机字节各写 3 次取中位:写延迟、按 id 读回(SELECT data)、sha256 比对、投影查询(`SELECT id, mime, size`)延迟、目录体积;另测单事务(BEGIN..COMMIT)含 20MB 写。脚本:`s2-bytes-perf.mjs`。

**原始关键输出**:
```
DEFINE FIELD data TYPE bytes: OK
1MB ×3:  write中位=10ms read中位=1ms  投影中位=1.0ms hash一致=true 体积增长=3.0MB(写入3MB原始)
5MB ×3:  write中位=34ms read中位=3ms  投影中位=3.5ms hash一致=true 体积增长=15.0MB(写入15MB原始)
20MB ×3: write中位=84ms read中位=11ms 投影中位=7.3ms hash一致=true 体积增长=60.0MB(写入60MB原始)
SELECT id,mime,size FROM audio (9 行含 9 个大值): 8.5ms
SELECT count(): 0.6ms
单事务 BEGIN..COMMIT 含 20MB: OK 105ms; 读回 size=20971520 mime=audio/ogg
最终库体积: 98.0 MB(原始写入约 98 MB)
```

**结论:通过,余量巨大**。阈值"20MB 单条写+读 < 2s"实测 84ms + 11ms,快 20 倍以上;膨胀比 ≈ 1.0x(98MB 原始 → 98MB 磁盘);单事务含 20MB 写 + 后续 UPDATE 稳定;字节读回逐位一致(sha256)。投影查询有轻微随大值总量增长的趋势(1.0→3.5→7.3ms,表内 3→9 个大行),9 行 98MB 大值时仍只 8.5ms——未被大值实质拖累,`SELECT count()` 0.6ms 完全无感。

**对 R 系列(Gate)**:**R2 音频取"入库 bytes"方案(首选)成立**,单库单事务边界拿到;无需退"元数据表+磁盘文件"兜底。注意读回类型是 Uint8Array 系(spike 里做了兼容判断),消费侧转 Buffer 即可。

## S3 · 事务写写冲突的真实错误形状

**方法**:① 同进程第二个 Surreal 实例连同一 surrealkv 路径;② 单连接并发两个 `query()`,各含 `BEGIN; LET $cur=(SELECT VALUE n FROM ONLY doc:one); SLEEP 500ms; UPDATE …; COMMIT;` 强制交错;③ 10 并发含 SLEEP 的事务打同一记录。脚本:`s3-tx-conflict.mjs`。

**原始关键输出**:

- 途径A(双实例同路径):第二个 `connect()` **无限阻塞不报错**(首跑 >120s 无返回,加 8s 超时后确认仍阻塞)。嵌入式 surrealkv 文件锁独占,同进程也不能开第二连接——**单进程必须单连接**,这与现有 connect.ts 单连接架构一致。
- 途径B(单连接并发 query,真造出冲突):
  ```
  tx1 成功
  [tx2 失败] 类名=InternalError name=InternalError
    message=Query not executed: Transaction conflict: Transaction write conflict. This transaction can be retried
    code=0
    kind='Internal'
    ownKeys=["stack","message","kind","code","details"]
    /failed transaction/i 匹配=false
  ```
- 途径C(10 并发):成功=3 失败=7,失败错误形状同上;最终 n=1(快照隔离:成功者都从 n=0 读起,写 n=1——**并发自增必须靠"重读+重试"而非并发事务堆叠**)。

**结论**:
- 嵌入式引擎**并发语义 = 真并发 + 乐观事务**:单连接上并发 `query()` 并不串行,交错事务在 COMMIT 处真实冲突。
- 冲突错误确切形状:JS 侧 `InternalError`(SDK 类),`kind='Internal'`,`code=0`,message 固定为
  **`Query not executed: Transaction conflict: Transaction write conflict. This transaction can be retried`**。
- **现有 `isTransientPersistError` 的 `/failed transaction/i` 匹配不到它**(`surreal-product-state-repository.ts:133-135`)——3.0.2 的措辞已换代,现行重试阶梯对真实引擎冲突完全失效。

**对 R 系列(Gate)**:R3 实体命令 + 乐观锁重试的硬前提**满足**,但判别式必须先修:建议改为
`/failed transaction|transaction conflict|can be retried/i`(三段并联,兼容旧措辞;"can be retried" 是引擎自己声明的可重试信号,最语义化)。这是**独立于 R3 的现货 bug**,可提前单独修(P8)。

## S4 · versioned surrealkv

**方法**:`surrealkv+versioned://<path>`(含 `surrealkv+versioned:<path>` 变体)连接;订阅 SDK `connecting/connected/error` 事件抓底层错误;普通库上直接试 `VERSION` 子句探语法;普通库→versioned 重开。脚本:`s4-versioned.mjs` / `s4b` / `s4c-wait20`。

**原始关键输出**:
```
== versioned 绝对路径: surrealkv+versioned:///…/data-s4/vdb ==
  [event:connecting] []
  connect 结果: Error: TIMEOUT-6s      (20s 变体同样超时;目标目录根本没被创建)
  [event:disconnected] []               (error 事件从未触发)

== 对照 surrealkv:// ==
  [event:connected] [ 'surrealdb-3.0.2' ]
  普通库 VERSION 子句报错: InternalError: There was a problem with the key-value store:
    There was a problem with a transaction: Invalid argument: Versioning not enabled
```

**结论:versioned 在 @surrealdb/node 3.0.3 不可用**。
- JS 胶水层注册了 `"surrealkv+versioned"` 引擎键(`@surrealdb/node/dist/surrealdb-node.mjs:549`),但原生 `SurrealNodeEngine.connect()` 对该 scheme **永不 settle**(20s 无结果、无 error 事件、数据目录都不创建)——胶水层 `#initialize` 的 catch 只 publish error 事件不 reject connect promise,雪上加霜地把挂死变成静默(`engine.ts` 同文件可见)。
- `VERSION` 子句语法本身在 3.0.2 SurrealQL 里**存在且解析通过**:`SELECT * FROM t VERSION d"2020-01-01T00:00:00Z";` 语法合法,运行时报 `Versioning not enabled`——即语法是 `VERSION d"<ISO时间>"`,但没有任何办法在嵌入式 Node 下开启 versioning。
- "非 versioned 库事后打开为 versioned":**无法测**(versioned 根本连不上),问题失效(moot)。

**对 R 系列**:R6 备份故事**不能**建立在 versioned surrealkv 上;退回方案自身的兜底(export/快照/JSON 导出契约)。若将来升级 @surrealdb/node,先重跑本 spike(脚本可复用)。

## S5 · 中文 ngram 调参 A/B

**方法**:语料取 `scripts/personas/*.json`(十个人物的 bio/stances/seed)切句,48 条、均长 38 字,含真实人名(陈知行/苏曼)与术语(数据飞轮/强化学习/预训练数据配比)。两个独立 surrealkv 库分别 `DEFINE ANALYZER zh TOKENIZERS class FILTERS ngram(2,2), lowercase`(现行)与 `ngram(1,3), lowercase`(候选),各建 `FULLTEXT ANALYZER zh BM25` 索引灌同样语料。10 个查询(单字×2/双字×2/人名×2/四字术语×2/长短语×2),每查询双打法:裸 `@@` 与生产同款 `search::analyze` 切 token 后逐 token `@@` OR 串联(`surreal-product-state-repository.ts` 打法)。脚本:`s5-ngram-ab.mjs`。

**原始关键输出**:
```
[A ngram(2,2) 现行] 索引构建 240ms,库体积 232KB
[B ngram(1,3) 候选] 索引构建 272ms,库体积 600KB
  [单字]「卡」   expect=5 | A: bare=0 or=0 top3=× | B: bare=5 or=5  top3=√
  [单字]「赌」   expect=5 | A: bare=0 or=0 top3=× | B: bare=5 or=5  top3=√
  [双字]「压缩」 expect=1 | A: bare=1 or=1 top3=√ | B: bare=1 or=3  top3=√
  [三字人名]「陈知行」expect=1 | A: bare=0 or=1 top3=√ | B: bare=1 or=6 top3=√
  [四字术语]「强化学习」expect=1 | A: bare=0 or=1 top3=√ | B: bare=0 or=10 top3=√
  [长短语]「预训练数据配比」expect=1 | A: bare=0 or=6 top3=√ | B: bare=0 or=10 top3=√
召回胜负: A 胜 0 / B 胜 2
索引构建: A=240ms B=272ms (1.1x) | 库体积: A=232KB B=600KB (2.59x)
```

**结论:ngram(1,3) 值得升级,代价明确**。
- **收益集中且真实**:单字查询 A 全灭(0 召回,ngram 最小 2 无 1-gram token)、B 全中且 top3 正确;三字人名裸 `@@` A 也 miss(B 命中)。多字查询两边 top3 全对(BM25 排序兜住了)。
- **代价一:体积 2.59x**(232KB→600KB,含数据基底,纯索引膨胀更高)。对现库 rag_chunk/memory 的文本量要乘系数预估;构建耗时基本持平(1.1x)。
- **代价二:精度噪声**:B 的 OR 展开命中数显著变多(1→10,1-gram posting list 长),意味着大语料上 BM25 打分工作量上升、长尾命中变宽。top3 排序本次未受损,但语料只有 48 条,大库上需复核。
- 生产查询侧同步注意:`search::analyze('zh', query)` 在 (1,3) 下 token 数暴涨,现行"逐 token OR"要加 token 上限/去重(spike 里 cap=12 可用)。

**对 R 系列**:R4 建议升级 `ngram(1,3)`,同时:① 预估真实语料索引体积(乘 ~2.6);② 查询侧 token cap;③ 上线用 REBUILD INDEX,注意 R4 已计划。若体积不可接受,退而求其次 `ngram(1,2)` 可另测(脚本改一个参数)。

## 决策矩阵

| Spike | 结论 | Gate 判定 | 对 R 系列的决策 |
|---|---|---|---|
| **S1** live/changefeed | live **可用但仅 unmanaged 路**(`LIVE SELECT`→`liveOf`;managed `.live()` 静默坏);changefeed **完全可用**(BigInt versionstamp + CHANGEFEED 表触发 stderr dbg 噪声) | 非阻塞项,超预期 | R5 可做真推送(liveOf)+游标轮询兜底;R1 的 `CHANGEFEED 7d` 功能成立但先评估 stderr 噪声量 |
| **S2** 大 bytes | **通过,余量 20 倍+**:20MB 写 84ms/读 11ms/hash 一致/单事务 OK/膨胀 ~1.0x/投影查询不受实质拖累 | **硬 Gate 通过** | **R2 音频定案"入库 bytes"**,不需要磁盘文件兜底方案 |
| **S3** 事务冲突 | 嵌入式=单连接内**真并发+乐观事务**;冲突错误 `InternalError`:"…Transaction conflict: Transaction write conflict. This transaction can be retried";**现行 `/failed transaction/i` 匹配不到**;同路径第二连接无限阻塞 | **硬 Gate 通过**(但判别式必须先修) | R3 乐观锁+重试可行;**先行修 P8**:判别式扩为 `/failed transaction\|transaction conflict\|can be retried/i`;保持单进程单连接 |
| **S4** versioned | **不可用**:`surrealkv+versioned://` 连接永不 settle(无报错、无目录);`VERSION d"…"` 语法存在但 "Versioning not enabled" 无法开启 | 非阻塞项,阴性 | R6 备份**放弃 versioned**,走 export/快照/JSON 导出;升级 @surrealdb/node 后重跑 s4 脚本 |
| **S5** ngram A/B | (1,3) 单字/人名召回从 0→全中,top3 无回退;代价=体积 2.59x + OR 命中变宽(大库精度需复核),构建耗时持平 | 非阻塞项 | R4 **升级 `ngram(1,3)`**,配套:体积预估×2.6、查询侧 token cap、REBUILD INDEX;体积超标则退测 `ngram(1,2)` |

**总判定:R0 全绿放行。** S2/S3 两个硬前提均满足(S3 附带挖出现货 bug:重试判别式失效,建议独立先修);S4 唯一阴性结论只影响 R6 备份路线的选型,已有兜底。
